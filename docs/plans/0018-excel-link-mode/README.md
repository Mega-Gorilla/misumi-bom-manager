## 要約

作るべきものは「保存時に元 Excel へ書き戻す**同期**」ではなく、**排他的な編集権（トークン）の受け渡し**。
アプリは `.xlsx` を文書として開くエディタになり、**同時に2人が書く状態を OS レベルで発生させない**。
これにより双方向マージ・競合解決・行 ID がすべて不要になる。

| 状態 | 書き手 | アプリのグリッド | Excel |
|---|---|---|---|
| アプリが編集権を保持 | アプリのみ | 編集可 | 読み取り専用でしか開けない |
| Excel が編集権を保持 | Excel のみ | 読み取り専用ビュー | 通常編集 |

アプリを終了せずに Excel で編集したい場合は、「Excel で編集」ボタンで**明示的に編集権を渡す**。
同時編集のみ引き続き禁止。

## 正本の分割（フィールド単位の所有権）

| データ | 正本 |
|---|---|
| BOM 入力列（型番・数量・品名・注文番号・独自列） | **Excel** |
| EC 取得値・価格履歴・マッピング設定・指紋・同期状態 | **DB**（BOM 行については未保存編集のジャーナルのみ） |
| アプリ画面 | Excel と DB を合成したビュー |

## 調査で判明した確定事実（すべて実測）

| # | 事実 | 根拠 |
|---|---|---|
| 1 | 現行の書き出しは**新規ブックを作る**ため同期に使えない（他シート・数式・書式が消え、全セルが文字列化） | `spreadsheet.rs:161` |
| 2 | 読み込みに **5,000 行の上限**があり、切り捨て結果で書き戻すと以降の行を消す | `spreadsheet.rs:13` |
| 3 | 列の所有権の混在が**実在**（`partsName ← product.name` の `overwrite` リンク） | 実 DB 調査 |
| 4 | 数式セルは**すでに計算結果として読めている**（`["4","8","CBT3-4"]`）→ 空欄扱いは**回帰** | 実 Excel 生成 + `calamine` 実測 |
| 5 | **OS レベルの排他は機能する**（writer=BLOCKED / reader=ALLOWED） | deny-write ハンドルで実測 |
| 6 | **Google Drive が G:/H: にストリーミングマウント**。ロックは同一マシン内のみ有効 | `GoogleDriveFS` 稼働確認 |
| 7 | **ロック保持中はアプリ自身も保存できない**（同一プロセスの再オープンも原子的置換も BLOCKED。`FILE_SHARE_DELETE` を足しても不可） | 実測（§4.9） |
| 8 | **dirty-cell 更新だけでは数式のキャッシュ値が古いまま残る**（ライブラリに計算エンジンがないため） | §4.4.1 |

## 決定事項

**複数人の同時編集は非対応**（PR #19 で合意 / plan.md §6.0）。OS ロックは**別マシンの Excel に効かない**ため
排他が成立せず、Drive が競合コピーを生成する。指紋比較による**検知と警告**（防止ではない）が限界であり、
**同時に触るのは1人という運用前提**の上に成り立つ機能である。外部変更を検知した場合は**自動マージせず**警告する。

## 最大のリスク

**read-modify-write ライブラリが成立するか**（§6.1）。`rust_xlsxwriter` は新規作成専用のため使えず、
候補ライブラリもセルを部分更新できて**未対応の Excel 要素を保存時に落とす**可能性がある。
ここが崩れれば設計ごと見直しになるため、**他に手を付ける前に技術検証で潰す**。

次いで **クラウド同期環境でのロック挙動**（§6.2・未検証）。§3.5 の排他の実測は**ローカルディスクでの結果**で、
Google Drive のストリーミングドライブ（G:/H:）上で同じ挙動になるかは不明。同期クライアントとの競合も未検証。
不成立ならリンクモードを**ローカルディスク限定**に退避する。

## 期待値

**「常に Excel が最新」ではない。** 正確には「**Excel が書き込み可能になり次第、最新へ同期**」。
ロック・クラッシュ・権限エラーがある以上、完全な即時同期は保証できない。

## 実装順序（概要）

1. **Google Drive 上でのロック挙動の検証**（不成立ならローカル限定に退避）
2. **read-modify-write の技術検証**（数式・書式・複数シート保持／数式セル識別／dirty-cell 更新／
   保持ハンドルへのストリーム書き込み／`calcPr fullCalcOnLoad`）
3. **ロック保持と保存の両立方式の決定**（案 A ハンドル渡し / 案 B 一時解放→置換→再取得）
4. **数式キャッシュ陳腐化の方針決定**（`fullCalcOnLoad` ＋ 未再計算セルの無効扱い）
5. **実ファイルでの保持テスト**
6. 同期メタデータの DB 設計 → 7. 編集権トークンの状態機械 → 8. アプリ所有列の書き戻し
→ 9. 外部変更検知・反映待ち → 10. 再読込 → 11.（必要なら）ファイル監視
