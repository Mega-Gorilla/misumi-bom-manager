Excel を BOM の正本（唯一のエディタ）とし、アプリは**読み取りと EC 列の書き戻しに徹する**ことで、

## 要約

**アプリは Excel の「相棒」であり、エディタではない。** 編集は **Excel に集約**する（PR #19 で合意）。

> **判断の理由**: Excel 互換のアプリケーションを作るのは困難であり、そこは**意図的に切る**。
> アプリ側の機能を制限することで実装を大幅に簡略化できる。

| 役割 | 担当 |
|---|---|
| **BOM の編集**（セル値・行・列・数式） | **Excel のみ** |
| **読み取り** | アプリ。**Excel が開いていても可能**（実測） |
| **EC 列の書き戻し** | アプリ。**Excel が閉じている時のみ**。開いていれば「反映待ち」 |

アプリはユーザーのデータを一切書かないため、**ファイルロックを保持する必要がない**。これにより
**編集権トークンの受け渡し**と**編集ジャーナル**が不要になった。**Excel は開きっぱなしでよい**。

> **競合窓について**: 恒久ロックに伴う問題は解消したが、**書き込み直前から原子的置換までの短い競合窓は残る**
> （排他保持と原子的置換は両立しないため。実測）。MVP では**楽観的競合検出**として扱う。
> ただし**バックアップ付き原子的置換**（`ReplaceFileW`）により、**競合は事後に確実に検出でき、
> 外部版も失われない**ことを**ローカル NTFS と Google Drive のミラーフォルダの双方で実測済み**。
> **ただしこれが保証するのはファイルシステム上の動作のみ**で、**同期クライアントとの競合は未検証**。
> plan.md §4.2.2 / §3.8 / §6.2

## 操作の流れ

| 操作 | 動作 |
|---|---|
| 「**Excel で編集**」ボタン | **Excel を開くだけ**（ロックも受け渡しも無い） |
| 「**更新**」ボタン | 手動で再読込 → 構造検証 → 再合成 |
| **Excel が保存された**（自動） | 監視で検知 → 再読込 → 構造検証 → 再合成（**安全判定が「安全」の時のみ自動適用**） |
| 「**Excel へ反映**」 | 指紋照合 → Excel が閉じていれば EC 列を書く／開いていれば**反映待ち** |

**アプリは未保存状態を持たない**ため、自動再読込で**失うものが無い**（＝安全に成立する）。

## 正本の分割（フィールド単位の所有権）

| データ | 正本 |
|---|---|
| BOM 入力列（型番・数量・品名・注文番号・独自列） | **Excel** |
| EC 取得値・価格履歴・マッピング設定・構造契約・指紋・同期状態 | **DB** |
| アプリ画面 | Excel と DB を**合成したビュー** |

## MVP のかたち

リンク BOM では**アプリは読み取り専用**。行・列・数式・セル値のすべてを Excel が管轄し、
読み込み時に**構造を検証**する（安全／要確認／破綻の3判定・plan.md §4.9）。
**不明な構造を推測して同期しない**のが原則。

その結果、リンクモードのアプリに残るのは **EC 取得／履歴／合計／カート投入／閲覧**で、
**セル編集・行追加・複製・削除・列追加/削除は無効化**される（従来 BOM では従来どおり。両モード共存）。

## 調査で判明した確定事実（すべて実測）

| # | 事実 | 根拠 |
|---|---|---|
| 1 | **Excel が開いていてもアプリは読める**（書き込みと原子的置換のみ BLOCKED。`~$` が検出手段） | 実 Excel(COM) で実測（§3.5） |
| 1b | **バックアップ付き原子的置換**（`ReplaceFileW`）は、置換された実ファイルをその瞬間のまま退避するため、**指紋照合後・置換直前の競合も検出でき、外部版が失われない** | 実測（§4.2.2） |
| 2 | 現行の書き出しは**新規ブックを作る**ため同期に使えない（他シート・数式・書式が消え、全セルが文字列化） | `spreadsheet.rs:161` |
| 3 | 読み込みに **5,000 行の上限**があり、切り捨て結果で書き戻すと以降の行を消す | `spreadsheet.rs:13` |
| 4 | 列の所有権の混在が**実在**（`partsName ← product.name` の `overwrite` リンク） | 実 DB 調査 |
| 5 | 数式セルは **Excel が最後に保存したキャッシュ値として読めている**（空欄扱いは**回帰**）。ただし**現在の正しい計算結果である保証はない** | 実 Excel 生成 + `calamine` 実測 |
| 6 | **dirty-cell 更新だけでは数式のキャッシュ値が古いまま残る**（ライブラリに計算エンジンがないため） | §4.4.1 |
| 7 | `calamine` の **`worksheet_formula` で数式の有無を取得できる**。ただし値と数式の Range は**原点が異なり**、`used_cells()` は範囲相対座標を返すため、**素直に対応づけると静かに1列ずれる** | 実測（§3.4.1） |
| 8 | **信頼できるワークブック識別子は存在しない**（`xr:revisionPtr documentId` は `mc:Ignorable` の Excel 独自拡張で、コピーすると複製される）。**MVP はパスを同一性の根拠**とする | 実測（§3.7） |
| 9 | **Google Drive は「ミラーモード」で、実ファイルはローカル NTFS 上にある**（`H:\マイドライブ` → `C:\GoogleDrive_hahahadesu`）。G:/H: が FAT32 を報告するのは仮想入口にすぎない | 実測（§3.6） |
| 10 | **`ReplaceFileW` は Drive のミラーフォルダ上でも成立**（置換・バックアップ・競合検出・外部版保全とも）。**ただし保証はファイルシステム上の動作まで**で、**同期クライアントとの競合は未検証**（§6.2） | 実測（§3.8） |
| 11 | ファイルロックは**同一マシン内でのみ有効**（別マシンの Excel には効かない） | `GoogleDriveFS` 稼働確認 |

> **不採用の記録**: アプリが deny-write ロックを保持して Excel を読み取り専用に強制する案も検討したが、
> **アプリ自身も保存できなくなる**ことが実測で判明した（`FILE_SHARE_DELETE` を足しても不可）。
> 「編集は Excel に集約」の決定により、この問題ごと不要になった（§3.5）。

## 決定事項

**複数人の同時編集は非対応**（plan.md §6.0）。ファイルロックは**別マシンの Excel に効かない**ため
排他が成立せず、Drive が競合コピーを生成する。指紋比較による**検知と警告**（防止ではない）が限界であり、
**同時に触るのは1人という運用前提**の上に成り立つ。外部変更を検知した場合は**自動マージせず**警告する。

## 最大のリスク

**read-modify-write ライブラリが成立するか**（§6.1）。`rust_xlsxwriter` は新規作成専用のため使えず、
候補ライブラリもセルを部分更新できて**未対応の Excel 要素を保存時に落とす**可能性がある。
ここが崩れれば設計ごと見直しになるため、**他に手を付ける前に技術検証で潰す**。

次いで **クラウド同期クライアントとの相互作用**（§6.2・**未検証**）。ファイルシステム上の動作は実測済みだが、
**同期がリモート変更を適用する瞬間との競合・置換後にリモート変更が到着する場合・競合コピーへの分岐**は
未検証。**実同期 PoC が不成立なら、クラウド同期フォルダへの書き戻しを無効化**する。
なお**競合コピーは MVP では確実な検出を保証しない**（同時編集をしない運用前提）。

## 期待値

**「常に Excel が最新」ではない。** 正確には「**Excel が書き込み可能になり次第、最新へ同期**」。
Excel が開いている・クラッシュ・権限エラーがある以上、完全な即時同期は保証できない。

## 実装順序（概要）

**ステップ 1〜3c は技術検証**で、ここで設計の成否が決まる。

1. **read-modify-write の技術検証**（数式・書式・複数シート保持／数式セル識別／dirty-cell 更新／`calcPr fullCalcOnLoad`）
2. **数式 PoC**（`stale` の発生頻度を測り MVP 境界を決定）
3. **構造変更 PoC ＋ 実ファイル保持テスト**
3b. **環境判定 PoC**（実体パス・実体ボリュームの解決／ミラー・ストリーミング判定）
3c. **実同期 PoC**（リモート変更の適用との競合／競合コピー／オフライン復帰。**不成立ならクラウド書き戻しを無効化**）
4. 構造契約の DB 設計 → 5. 読み込み＋構造検証＋合成ビュー → 6. アプリ所有列の書き戻し
→ 7. 反映待ち・外部変更検知 → 8. リンクモード UI → 9. ファイル監視による自動再読込
