# Excel リンクモード 詳細計画

Excel を BOM の正本（唯一のエディタ）とし、アプリは**読み取りと EC 列の書き戻しに徹する**ことで、
インポート／エクスポートの手動往復をなくす機能の詳細計画。

- 関連 Issue: [#18](https://github.com/Mega-Gorilla/misumi-bom-manager/issues/18)
- ステータス: **計画中・未着手**（本ドキュメントの合意 → 技術検証 → 実装）

---

## 1. 目的

現状は Excel の**インポート／エクスポート**方式で、DB が正本（system-of-record）。BOM を更新するたびに
手動の取込・書き出しが必要で、Excel とアプリの内容が容易に乖離する。

**Excel を実質的な BOM マスターとして使い、常に最新に保つ**のが目的。

## 2. 結論：アプリは Excel の「相棒」であり、エディタではない

「DB を正本に保ったまま保存時に元 Excel へ書き戻す」＝**双方向同期**は、2つの正本を常に一致させ続ける
という最も難しい問題を引き受けることになる。ユーザーが Excel を編集する前提なら、**Excel を正本と認めた上で
DB を従属させる**のが正しい。

そのうえで、**編集を Excel に集約する**という製品判断を採る（PR #19 で合意）。

> **判断の理由**: Excel 互換のアプリケーションを作るのは困難であり、そこは**意図的に切る**。
> アプリ側の機能を制限することで実装を大幅に簡略化できる。

この結論により、**アプリはユーザーのデータを一切書かない**。したがって:

- **ファイルロックを保持する必要がない**（保持する理由は「アプリで編集させること」だけだった）
- **編集権トークンの受け渡し**と**編集ジャーナル**が不要になる
- **Excel は開きっぱなしでよい**。アプリは書き込みを保留するだけ

> **ただし「ロックと保存の板挟み」は完全には消えない。** 恒久ロックの版は消えたが、
> **書き込みの瞬間に縮小した形で残る**（排他保持と原子的置換は両立しないため）。§4.2.2 で扱う。

| 役割 | 担当 |
|---|---|
| **BOM の編集**（セル値・行・列・数式） | **Excel のみ** |
| **読み取り** | アプリ。**Excel が開いていても可能**（§3.5） |
| **EC 列の書き戻し** | アプリ。**Excel が閉じている時のみ**。開いていれば「反映待ち」（§3.5） |

**期待値の正確な表現**: 「常に Excel が最新」ではなく、
**「Excel が書き込み可能になり次第、最新へ同期」**（§6.4）。

## 3. 調査結果（すべて実測・本計画の根拠）

### 3.1 現行の書き出しは同期に使えない

`src-tauri/src/spreadsheet.rs:161` の `write_xlsx` は既存ブックを開かず `XlsxWorkbook::new()` で
**新規作成**する。元ファイルへ保存すると次が失われる。

- 他シート（`add_worksheet()` を1回しか呼ばない）
- 数式
- 書式・列幅・結合セル・条件付き書式・図形・グラフ
- セル型（全データが `write_string` で**文字列**として書かれる → 数量が文字列になり `SUM` が壊れる）

→ **既存ファイルの一部セルのみを更新する read-modify-write 方式への置換が前提条件**（§7）。

### 3.2 読み込みに 5,000 行の上限がある

`src-tauri/src/spreadsheet.rs:13` の `MAX_ROWS = 5000`。切り捨てられた読み込み結果を元に元ファイルを
書き換えると、**5,000 行目以降を消す**。

→ **`truncated` なファイルには絶対に書かない**ガードが必須。検知には既存の `SheetGrid.truncated` を使う。

### 3.3 列の所有権の混在が実在する

「supplier 列以外は編集可能」（`src/lib/columns.ts`）であり、`ColumnLink.write` により
**取得した EC 値を編集可能なユーザー列へ書き込む**ことができる。実 DB を調査した結果、
これは仮説ではなく**実在**した。

```
bom_id=4388601c…  key=partsName  kind=core  editable=1
  link_field=product.name   link_write=overwrite
```

（BOM 2件中1件。`link_write` を持つ列は全 16 列中この 1 列のみ）

### 3.4 数式セルは Excel が最後に保存したキャッシュ値として読めている

Excel は数式セルに**数式 `<f>` とキャッシュ値 `<v>` の両方**を保存する。実 Excel（COM）で生成した
ファイルの `xl/worksheets/sheet1.xml` を直接確認した結果:

```xml
<c r="A1"><v>4</v></c>
<c r="B1"><f>A1*2</f><v>8</v></c>
<c r="C1" t="str"><f>CONCATENATE("CBT3-",A1)</f><v>CBT3-4</v></c>
```

`calamine` はこの `<v>` を読むため、現行の `read_workbook` は既に値を返している（実測 `["4", "8", "CBT3-4"]`）。

**正確な表現**（初版の「数式セルは『値』として**正しく**読めている」は過剰主張だったため訂正）:

> 数式セルについて、**Excel が最後に保存したキャッシュ値**を読み取れている。ただし、その値が
> **現在の入力セルに対して再計算済みかは、ファイルだけからは保証できない**。

Excel が**手動計算モード**だった場合や、外部ツールが依存セルだけを書き換えた場合、Excel 由来の
ファイルであってもキャッシュが古い可能性がある。→ 計算状態のモデル化が必要（§4.4）。

→ それでも **数式セルを「空欄として取得」する案は回帰**である。数量が `=A1*2` なら数量が空になり
小計・カート投入数量が壊れ、型番が数式なら行が EC 取得の対象外に落ちる。

#### 3.4.1 `calamine` は数式の有無を取得できる（ただし座標系に罠がある）

`calamine 0.26` は `worksheet_range`（値）に加えて **`worksheet_formula`（`<f>` の数式文字列）**を持つ。
現行の `spreadsheet.rs` は `worksheet_range` しか呼んでいないため、**値は読めるがそのセルが数式かどうかを
アプリへ渡していない**。既存 API で拡張可能（実測）。

**【実装上の罠・要注意】** 2つの Range は**原点が異なり**、`used_cells()` は**範囲相対座標**を返す。
そのまま添字で対応づけると**静かに1列ずれる**（実測）:

```
VALUES   start=Some((0, 0)) size=(1, 3)   ← A1:C1
FORMULAS start=Some((0, 1)) size=(1, 2)   ← B1:C1（数式のある最初のセルが原点）

-- NAIVE（範囲相対のまま。誤り）--
   f="A1*2"                      paired value=Some(Float(4.0))    ← B1 の式に A1 の値(4)が付く
   f="CONCATENATE(\"CBT3-\",A1)"  paired value=Some(Float(8.0))   ← C1 の式に B1 の値(8)が付く

-- start() でオフセット（正しい）--
   f="A1*2"                      abs=(0, 1) paired value=Some(Float(8.0))
   f="CONCATENATE(\"CBT3-\",A1)"  abs=(0, 2) paired value=Some(String("CBT3-4"))
```

**必ず `formula_range.start()` を加算して絶対座標に変換してから値と対応づけること。**
これは誤りが例外にならず**誤ったデータとして通る**ため、単体テストで固定する（§7.1）。

### 3.5 【中核】Excel が開いていても読める。書けないだけ

実 Excel（COM）でワークブックを開いた状態での実測:

| アプリ側の操作 | 結果 |
|---|---|
| **読み取り**（`access=Read, share=ReadWrite`） | **ALLOWED** |
| 書き込み（`access=ReadWrite`） | **BLOCKED** |
| 原子的置換（`File.Replace`） | **BLOCKED** |
| `~$` オーナーファイル | **存在する**（＝Excel が開いていることの安価な検出手段） |
| Excel を閉じた後の書き込み | **ALLOWED** |

**これが本計画の中核**である。アプリは**いつでも読める**ので、ロックを保持する必要がない。
書き込みだけが Excel の在否に依存し、開いていれば「反映待ち」に落とせばよい（§4.2）。

> **参考（不採用の記録）**: 当初はアプリが deny-write ハンドルを保持して Excel を読み取り専用に強制する
> 案を検討したが、**アプリがユーザーのセルを編集する**場合にのみ必要な仕組みであり、§2 の決定により不要。
> なお実測では、その方式は**アプリ自身も保存できなくなる**という問題を抱えていた（保持中は同一プロセスの
> 再オープンも原子的置換も BLOCKED。`FILE_SHARE_DELETE` を足しても不可）。§2 の決定はこの問題ごと解消する。

### 3.6 Google Drive がストリーミングマウントされている

`GoogleDriveFS` 稼働中、**G: / H: がマウント**（OneDrive も稼働）。BOM リストという性質上、
共有ドライブ運用の可能性が高い。

**ファイルロックは同一マシン内でのみ有効**で、別マシンの Excel には一切効かない。
→ これを受け、**複数人の同時編集は非対応**と決定した（§6.0）。

### 3.7 信頼できるワークブック識別子は存在しない

実 Excel が生成した `xl/workbook.xml` を確認した結果:

```xml
<workbook mc:Ignorable="x15 xr xr6 xr10 xr2" …>
  <xr:revisionPtr revIDLastSave="0"
      documentId="8_{EB6920E8-C1D4-4BB6-B81C-C624C468635D}" …/>
  <calcPr calcId="191029"/>
</workbook>
```

`documentId` は存在するが、**識別子として信頼できない**。

- `xr`（2014 revision）名前空間は **`mc:Ignorable` に列挙**＝任意の拡張。Excel 以外の生成物には無い
- 共同編集のリビジョン用であり、**安定性が保証されない**
- **ファイルをコピーすると複製される**ため、原本とコピーを区別できない

`docProps/custom.xml` は**存在しなかった**（独自 GUID の注入は可能だが、それは**ファイルへの書き込み**であり、
§5 の「構造確認完了まで Excel へ絶対に書き込まない」と衝突する）。

| 候補 | 評価 |
|---|---|
| ファイルパス | 移動・改名で破綻。**MVP はこれを同一性の根拠とする**（破綻時は再リンクを促す） |
| `xr:revisionPtr documentId` | 上記の理由で**権威にしない**。「移動・改名の検出ヒント」までなら使える可能性（§7.2） |
| `docProps/custom.xml` へ独自 GUID を注入 | **書き込みが必要**。MVP 外 |
| 内容の指紋 | 保存のたびに変わる。**変更検知には使えるが同一性の根拠にはならない**（§4.6） |

**`calcPr` は実在し、`calcMode` 属性は省略されていた**（＝既定の自動計算）。したがって §4.4.1 の
`fullCalcOnLoad` 付与と `calcMode="manual"` 検出は、いずれも**属性レベルで実現可能**
（ライブラリが `calcPr` を保持できるかは §7 の検証対象）。

## 4. 設計

### 4.1 正本の分割（フィールド単位の所有権）

全体で正本を1つに決めるのではなく、**データごとに正本を分ける**。

| データ | 正本 |
|---|---|
| BOM 入力列（型番・数量・品名・注文番号・独自列） | **Excel** |
| EC 取得値・価格履歴・マッピング設定・構造契約・指紋・同期状態 | **DB** |
| アプリ画面 | Excel と DB を**合成したビュー** |

**アプリは未保存状態を持たない。** ユーザーのデータを編集しないため、編集ジャーナルも autosave も不要。
EC 取得結果は取得時点で DB に永続化される。

### 4.2 読み書きのタイミング（ロックは保持しない）

§3.5 のとおり **Excel が開いていてもアプリは読める**ため、**ロックは一切保持しない**。

| 契機 | 動作 |
|---|---|
| BOM を開く | Excel から読む（**Excel が開いていても可**）→ 構造検証（§4.9）→ DB と合成して表示 |
| **「Excel で編集」ボタン** | **Excel でファイルを開くだけ**（ロックも受け渡しも無い。単なる起動導線） |
| **「更新」ボタン** | 手動で再読込 → 構造検証 → 再合成 |
| **Excel が保存された**（自動・§4.2.3） | 監視で検知 → 再読込 → 構造検証 → 再合成 |
| EC 取得 | 結果を **DB へ保存**（Excel には触らない） |
| 「Excel へ反映」 | 指紋照合（§4.6）→ **Excel が閉じていれば**アプリ所有列を書く → 開いていれば**反映待ち**（§4.2.1） |

**ユーザーは Excel を開きっぱなしにしてよい。** アプリは書き込みだけを保留する。

#### 4.2.1 反映待ち（latest-wins）

**DB と Excel を1つのトランザクションにはできない。** 「DB 保存成功・Excel 更新失敗」は必ず起こり得るため、
**「反映待ち」状態は設計の一部**であって例外処理ではない。

- Excel が開いている／権限エラー／Drive 同期中 → **反映待ち**として記録し、UI に明示する
- 検出は `~$` オーナーファイルの有無（安価・§3.5）で予告し、**権威は実際の write-open 試行**とする

**保留するのは「書くべきセル値」ではなく「反映すべき EC 取得世代と対象 BOM」。** Excel が開いている間に
EC 取得を複数回行っても、古い要求を順に書く必要はない。

- **latest-wins**: 古い反映要求は**最新の DB 状態へ統合**する（キューに積まない）
- **再試行時に必ず Excel を再読込**し、**現在行と最新の DB 値からアプリ所有列を再生成**する（§4.5）
  — 保留中に Excel 側で行が増減していても正しく反映できる
- 権限エラーなど**恒久的な失敗は無限再試行しない**。手動再試行・解除を提示する

**再試行の契機**は「Excel が閉じられた（＝書けるようになった）」こと。これは数式状態を `trusted` に戻す契機
（＝**再計算後に保存されたファイルを正常に再読込した**こと。§4.4.1）とは**別物**なので混同しない。

#### 4.2.2 書き込みの手順と競合窓

1. **指紋照合**（§4.6）— 変化していれば書かず、再読込を促す
2. **再読込 → 構造検証**（§4.9）— 破綻・要確認なら**書かない**
3. **アプリ所有列を行単位で再計算**（§4.5）
4. **配列・スピル範囲との交差検査**（§4.4.2）— 交差または範囲を識別できなければ**書かない**
5. **バックアップ**を取る
6. read-modify-write で一時ファイルを生成し、`calcPr fullCalcOnLoad` を付与（§4.4.1）
7. **置換直前にもう一度指紋を照合**（窓を最小化する）
8. **原子的置換**
9. **置換後に読み返して検証**し、新しい指紋と計算状態を記録する（§4.4.2）

ロックを保持しないため、書き込みハンドルは**この瞬間だけ**取得する（自らを締め出す問題は起きない）。

##### 競合窓は狭められるが、消せない

**原子的置換が保証するのは「途中状態を見せないこと」であって、「確認した版だけを置換する」
compare-and-swap ではない。** 最後の指紋照合から置換までの間に他プロセスが保存すれば、その変更を上書きしうる。

**この窓を消すには置換の間ファイルを排他保持する必要があるが、§3.5 の実測どおり
「排他保持」と「原子的置換」は両立しない**（deny-write を保持すると `File.Move`/`Replace` が
BLOCKED になり、`FILE_SHARE_DELETE` を足しても救済されなかった）。したがって二者択一になる。

| 案 | 競合窓 | 原子性 | 評価 |
|---|---|---|---|
| **B'（採用）**: ロックなし＋原子的置換 | **残る**（ミリ秒オーダー） | **あり** | 競合は**事後検出**する |
| A'（不採用）: 書き込みの間だけ deny-write 保持＋ハンドル経由で in-place 更新 | 無い | **無い**（truncate+全書き直し） | **書き込み中のクラッシュで master BOM が破損** |

**B' を採用する。** 稀な競合（検出可能）より、クラッシュによる BOM 破損（回復困難）の方が重大なため。
また Drive 上では A' が機能する保証も無い。

> **訂正**: 旧 §4.9 の「ロック保持と保存の板挟み」は、**恒久ロックの版が消えた**だけで、
> **書き込みの瞬間に縮小した形で残っている**。「消滅した」は言い過ぎだった。

**競合を検出したときの動作**:

- **自動復元して再上書きしない**（再度クロバーするため）
- 生成済みの一時ファイルを**競合コピーとして退避**し、**同期を停止**してユーザーへ提示する

**残余リスク（仕様として明示する）**: Excel が開いていれば書き込み自体が BLOCKED されるため、
現実的な競合相手は **Drive 同期クライアントや第三者ツール**である。Drive 上では
**完全防止ではなく楽観的競合検出**にとどまる。PoC 完了までは**ローカルファイルを前提**とする（§5）。

#### 4.2.3 Excel の保存を検知して自動再読込する

**アプリが読み取り専用になったことで、自動再読込が安全に成立する。** §4.1 のとおり
**アプリは未保存状態を持たない**ため、いつ再読込しても**失うものが無い**（編集可能な設計では、
自動再読込はユーザーの未保存編集を破棄しうるため許されなかった）。

- 既定で**自動再読込を有効**にする。「更新」ボタンは手動トリガとして併置する
- **安全判定（§4.9）の結果が「安全」の時だけ自動適用**する。**要確認・破綻は自動適用せず**、
  UI に提示してユーザーの確定を待つ
- 反映待ちがある状態で Excel が閉じられたら、書き込みを再試行する（上記）

**既知の落とし穴（§7.2 で検証する）**:

- Excel の保存は**一時ファイル書き出し → 原子的置換**であり、**イベントが複数回発火**する
  → **デバウンス**（最後のイベントから一定時間）が必要
- 原子的置換によって**ファイルの実体が入れ替わる**ため、パスではなく**親ディレクトリを監視**しないと
  監視が外れる可能性がある
- 保存の途中で読むと**失敗または部分読み**になりうる → **リトライ**する
- `~$` オーナーファイルの作成・削除もイベントを生む → **対象ファイル名でフィルタ**する

> **整合性の責任分界**: 監視は**利便性のためのトリガ**であり、**整合性の保証には使わない**。
> イベントは取りこぼしうる。正しさの根拠は常に**読み込み時の構造検証（§4.9）と
> 書き込み直前の指紋照合（§4.6）**にある。

### 4.3 列は二分する（所有権＝値の作者。`fillEmpty` は同期では成立しない）

**「列の所有権」と「ファイルへの書き込み主体」は別の概念**として定義する。

- **書き込み主体**: ファイルへ書くのは **Excel（ユーザー）とアプリ（アプリ所有列のみ）**
- **列の所有権**: その列の**値を作るのは誰か**

| 分類 | 値の作者 | アプリの書き込み | アプリのグリッド | Excel での編集 |
|---|---|---|---|---|
| **アプリ所有列** | EC 取得処理 | **毎回まるごと上書き** | 読み取り専用 | 物理的には可能。ただし**値は取り込まず**、次回取得時に**再生成**される |
| **ユーザー所有列** | ユーザー | **一切書かない** | 読み取り専用（§4.8） | **自由** |

アプリ所有列の Excel 上の値は、アプリにとって**再生成可能な派生値**であり、**DB の EC キャッシュ・
価格履歴へ取り込まない**（＝「Excel で編集しない**約束**」ではなく、「編集されても**無視する**」という**強制**）。

- Excel 上の手修正値を MISUMI 取得結果として採用しない
- EC 取得成功時は現在の取得結果で再生成する
- ヘッダ・セル色・コメント等で「**EC 自動更新列／次回取得時に更新**」と明示する

**ユーザーの手動値を業務値として使いたい場合**は、アプリ所有列を直接上書きせず、**別のユーザー所有列**を使う。

| 列 | 所有者 | 用途 |
|---|---|---|
| EC 単価 | アプリ | EC 取得結果 |
| 採用単価／手動単価 | ユーザー | 業務上の上書き値 |
| 小計 | アプリ | `採用単価 ?? EC 単価` から計算 |

> この「上書き列」は**現行アプリに無い新機能**（現状の小計は quote の単価から導出。§4.5）。
> **MVP には含めない**。アプリ所有列内でのセル単位の手動上書きを正式サポートするには、
> 上書き値・出所・日時・解除操作の管理が必要になるため MVP 外。

**`fillEmpty`（空欄補完）は継続同期では成立しない。** 一度アプリがセルを埋めると次回は「空でない」ため
更新対象から外れ、かといって上書きすればユーザーの手入力を消しうる。**「アプリが埋めた値」と
「ユーザーが入力した値」をセル単位で区別できない**以上、値は更新も削除もできず永久に陳腐化する。

`overwrite` / `fillEmpty` / `suggest` は本質的に**インポート時点の一回きりの概念**であり、同期には持ち込めない。

§3.3 で実在が確認された `partsName ← product.name (overwrite)` は、リンクモードでは
**「アプリ所有列として宣言する」か「`suggest` に落とす（アプリ内表示のみ）」の二択**をユーザーに選ばせる。

### 4.4 数式セルの扱い

**次の4つは別々の性質であり、混同してはならない。**

| 性質 | 成立するか |
|---|---|
| 数式を**保持**できる | ○（数式セルに書かなければよい） |
| キャッシュ値を**読める** | ○（`worksheet_range`。§3.4） |
| その値が**現在の正しい計算結果**である | **△ 保証できない**（§3.4・手動計算モード等） |
| アプリが**再計算**できる | **× できない**（OOXML 編集ライブラリに計算エンジンはない） |

したがって、数式セルごとに**計算状態**を持つ。

**初回読込を直ちに `trusted` とするのは誤り**だった（「証明できない」と書きながら状態名が「信頼済み」を
主張しており矛盾していた）。`unverified` を追加して4状態にする。

| 状態 | 意味 | 業務利用 |
|---|---|---|
| `unverified` | **初回読込値**。Excel が保存した時点のキャッシュだが、**再計算済みかを証明できない** | **可**（ただし未検証である旨を表示。下記の残余リスク） |
| `trusted` | **アプリ管理下で**「アプリが `fullCalcOnLoad` を付与 → Excel が開いて全再計算 → 保存 → アプリが再読込」まで**確認できた**値 | **可** |
| `stale` | アプリが書き込んで以降、再計算されていない | **不可**（表示のみ・警告） |
| `missing` | `<v>` が無い等で値を取得できない | **不可** |

`unverified` と `trusted` は**どちらも業務利用可**で、違いは**確証の有無とその表示**にある
（`unverified` はバナー等で「Excel が保存した時点の計算結果です」と明示する）。

> **残余リスク（仕様として明示する）**: `unverified` を業務利用可とするのは**意図的な妥協**である。
> Excel が手動計算モードだった、または第三者ツールが依存セルだけを書き換えた場合、初回値が
> 実際に古い可能性がある。これを不可にすると**リンク直後の BOM が一切使えなくなる**（Excel を開いて
> 保存するまで EC 取得もカート投入もできない）ため、実用性を優先して**可**とする。
> `<calcPr calcMode="manual"/>` を検出できた場合は警告を強める（§4.4.1）。

**読み取り時の保持項目**（`worksheet_range` と `worksheet_formula` を**同時に**読む。§3.4.1 の座標系の罠に注意）:

- 表示値 / 数式の有無 / 数式文字列 / 計算状態

数式セルには `fx` 表示を付ける（アプリでは全列が読み取り専用なので、編集ガードは §4.8 に包含される）。
初回読込の値は「**Excel が保存した時点の計算結果**」として表示する（絶対的な最新性は保証しない）。

#### 4.4.1 数式キャッシュの陳腐化

`B1 = A1*2` の状態でアプリが **A1 だけ**を書き換えても、OOXML 編集ライブラリは計算エンジンを持たないため
**B1 の `<v>` は古いまま**残る。直後に再読込すると、**数量・小計・カート投入数に古い値を使う**。

アプリはユーザー列を書かないが、**アプリ所有列（EC 単価など）を更新するだけでも起きる** —
ユーザーが `=EC単価*数量` のような数式を持っていれば、その `<v>` が陳腐化する。

**アプリが書き込んだ時点で、全数式セルを `stale` とする。**

依存関係グラフを持たないため「変更セルに依存する数式だけ」を正しく特定できない。数式文字列は
`worksheet_formula` で取得できるが、**安全な依存セル解析の自前実装は別規模の課題**であり
（名前付き範囲・構造化参照・`INDIRECT`/`OFFSET` 等で静的解析は破綻する）、MVP では**安全側に倒して
全数式セルを一括で `stale`** にする。

`stale` / `missing` の値は**業務利用しない**:

- EC 取得の型番 / 数量・小計・MOQ 判定 / カート投入数量 / 注文番号 / 合計・集計

表示は可能だが「未再計算」の警告を付ける。

**Excel ファイル側の扱い**:

- 既存の `<f>` を保持し、**数式セルには絶対に書き込まない**
- アプリがセルを書き換えたら、Excel が次回開いた時に再計算する設定を付与する
  （`fullCalcOnLoad`、必要に応じて `forceFullCalc`。§3.7 のとおり `calcPr` は実在する）
- 計算モード・計算チェーン（`calcChain.xml`）・動的配列・共有数式を RMW ライブラリが保持できるか検証する（§7.1）

**状態遷移**（Excel で再計算しただけではアプリへ結果は戻らないため、
「Excel で再計算 → 保存 → 閉じる → アプリが再読込」までを**一つの遷移**として扱う）:

```
Excel 保存済みキャッシュ
        ↓ アプリが初回読込（確証なし）
unverified（表示・業務利用可。「Excel 保存時の計算結果」と明示）
        ↓ アプリが Excel へ何か書く（fullCalcOnLoad を付与）
stale（表示のみ。EC 取得・カート投入には使わない）
        ↓ Excel が開いて全再計算 → 保存
        ↓ アプリが再読込して指紋の変化を確認  ← これが復帰の契機
trusted（表示・業務利用可）
```

**`trusted` へ戻る契機は「Excel を閉じたこと」ではなく、「再計算後に保存されたファイルを
正常に再読込したこと」**である。Excel の終了は**反映待ちの再試行**の契機であり（§4.2.1）、**別物**として扱う。

Excel を**保存せず**終了した場合は `stale` のまま残る（ファイルが変わっていないため）。

#### 4.4.2 計算状態の永続化と配列範囲

**計算状態は DB に永続化する。** アプリが書き込んで `stale` になったまま終了し、再起動後の
単純な初回読込で `unverified`（業務利用可）に戻ってしまうと、**安全策が失われる**。

MVP は**全数式セルを一括で `stale`** にするため、セル単位ではなく**対象シートまたはワークブック単位**の
永続化で足りる。保持する項目は §4.7 に含める。

**復元規則（指紋ベース）**:

| 起動時の照合 | 判定 |
|---|---|
| 現在の指紋 == **最後にアプリが書き込んだ直後の指紋** | 誰も保存していない → **`stale` のまま** |
| 現在の指紋 != 上記、かつ **再計算要求（`fullCalcOnLoad`）を付与済み** | Excel が開いて再計算・保存した → **`trusted`** |
| 再計算要求を付与しておらず、アプリの書き込み記録も無い | **`unverified`** |

> **残余リスク**: 「指紋が変わった＝Excel が再計算した」は厳密には証明でない（第三者ツールが
> 再計算せずに保存した場合を区別できない）。実用上の妥協として受け入れ、仕様に明示する。

##### 配列数式・動的配列（スピル）は書き戻し範囲の競合として扱う

アプリが読み取り専用になったため、スピル結果セルを**編集**する問題は消えた。**残るのは書き込みの衝突**である。

**ユーザー所有列の動的配列がアプリ所有列までスピルしている場合、EC 列の書き戻しがスピル範囲を破壊しうる。**
式がアンカーセルにしか保存されない形式では、**書き込み対象セルだけを見ても数式範囲だと判定できない**
（スピル結果セルは通常セルに見える）。

したがって書き込み前に（§4.2.2 手順4）:

- **配列数式・動的配列の対象範囲を識別する**（`<f t="array" ref="…">` 等）
- **書き込み対象セルと配列／スピル範囲の交差を検出する**
- **交差した場合は Excel への書き込みを禁止**する
- **範囲を安全に識別できない場合も書き込み禁止**にする（識別できないライブラリ・ファイルはリンク対象外）

> **検討**: `<calcPr calcMode="manual"/>` を検出できればリンク時に警告できる（キャッシュが古い蓋然性が高い）。
> ただしこれは**ヒューリスティックであって証明ではない**（`auto` でも第三者ツールが依存セルを書けば古くなる）。
> §7.1 で検出可否を確認する。

### 4.5 行 ID は不要（ただし派生列は行単位で計算する）

**訂正**: 初版では「EC 値は**型番の**純粋関数」と書いたが、これは**不正確**だった。実装を確認した結果:

- キャッシュ／履歴のキーは `parts_no` 単独ではなく **`(supplier_code, parts_no)`**（`db.rs` V1）
- キャッシュは **qty 非依存**（代表 qty=1 で取得。`src/api/bom.ts:74-75`）
- `quote.subtotal` は **`unitPrice × Qty × qtyMultiplier`**（`src/lib/columns.ts:159`）
- `messages` の MOQ 警告も**行の Qty に依存**する

既存実装はこれらを保存された値ではなく**行の現在値から都度導出**している
（`src/App.tsx:296-298`: "Subtotal and the MOQ note are derived **LIVE** ... so they stay correct
after the user edits Qty (no stale stamped values)"）。

正しくは、アプリ所有列の値は次の**純粋関数**である。

```
appOwnedValue = f(supplier, partNo, row qty, BOM qtyMultiplier)
```

したがって**書き込み直前に、現在の各行の supplier・型番・数量と BOM の数量倍率から再計算する**
（既存実装の LIVE 導出と同じ方針）。これにより:

- 同じ型番でも**行ごとに異なる値**（小計・MOQ 警告）を正しく書ける
- 依然として**冪等**であり、**行の同一性を必要としない**（行 ID 不要の結論は維持）

**行 ID が必要になるのは行単位の状態を持つ場合**（提案の採否、アプリ独自コメント、型番変更前後の行追跡）。
MVP では持たない。将来必要になれば隠し ID 列またはメタデータシートを検討する。

### 4.6 書き込み前の指紋照合

書き込み直前に**最終読込時の指紋と現在の指紋を比較**する。変化していれば古い行番号を信用せず、
**再読込 → 構造検証 → アプリ所有列を再計算 → 書き込み**。

指紋が変化していた場合、**自動マージは行わない**（§6.0）。ユーザーへ警告し、再読込を促す。

ファイル監視（§4.2.3）は**自動再読込のトリガ**であって、**整合性保証には使わない**。イベントは
取りこぼしうるため、正しさの根拠は常に**この指紋照合と読み込み時の構造検証（§4.9）**にある。

### 4.7 構造契約（同期メタデータ）

現在 `importedFrom`（ファイルパス）しか保持していない（`src/bom/ImportWizard.tsx:184`）。
リンク作成・再確認時に、**構造契約**として最低限これらを DB へ保存する（§4.9 の判定に必要）。

- **ワークブック識別子** — §3.7 のとおり信頼できる識別子は存在しない。**MVP はパスを同一性の根拠**とし、
  破綻時（移動・改名）は再リンクを促す
- 対象シート（名前またはシート ID）
- ヘッダ行・データ開始行
- **必須列・任意列**
- Excel 列 ↔ アプリ列キーの対応
- 読み飛ばした列
- 各列の role
- **アプリ所有／ユーザー所有**
- アプリ所有列の位置
- **最後に確認したヘッダ構成**
- **データ範囲**
- **構造フィンガープリント**（§4.9 用。内容の指紋（§4.6）とは別物）
- 同期状態とエラー

**計算状態と反映待ちの永続化**（§4.4.2 / §4.2.1。**対象シートまたはワークブック単位**で足りる）:

- **再計算要求中か**（`fullCalcOnLoad` を付与済みか）
- **最後にアプリが書き込んだ直後の指紋**（＝ `stale` 判定の基準）
- **最後に「Excel 保存後の読込」を確認した指紋**
- **現在の計算状態**（`unverified` / `trusted` / `stale` / `missing`）
- **反映待ちの EC 取得世代と対象 BOM**（セル値は保持しない。latest-wins・§4.2.1）

> 定義名（Defined Names）や Excel テーブルを追跡手段として使えるかは **PoC 対象**（§7.2）。
> ただし**既存 BOM を自動的にテーブル化してレイアウトへ影響を与えない**こと。

### 4.8 アプリは読み取り専用（編集は Excel に集約）

リンク BOM では、**アプリからの編集を一切行わない**。セル値・行・列・数式のすべてが Excel の管轄。

**既存機能への影響（無視できない）**: 現行アプリは以下を持っており、リンク BOM では**すべて無効化**される。

| 機能 | 場所 |
|---|---|
| セル編集（グリッド） | `src/lib/columns.ts`（supplier 列以外は `editable`） |
| 行追加 / 複製 / 行削除 | `src/bom/Toolbar.tsx:196-200`（メニュー）、`:296-299`（コマンドバー） |
| 列の追加・削除 | `src/bom/ColumnManager.tsx:172` ほか |

結果として、リンクモードのアプリに残るのは
**EC 価格・納期の取得／履歴閲覧／合計／カート投入／閲覧**となる。
従来 BOM ではこれらの機能は従来どおり使える（**両モードは共存する**。§5）。

> 数量倍率（`meta.qtyMultiplier`）は Excel ではなく **DB 所有のメタ情報**なので、リンクモードでも編集可能。

### 4.9 Excel 側の構造変更判定

Excel 側ではユーザーが行・列・数式を**自由に編集してよい**。ただし**読み込み時に構造を検証**し、
**安全性を確認できるまで Excel へ書き戻さない**。**不明な構造を推測して同期しない**ことが本節の中心。

| 判定 | 変更例 | 動作 |
|---|---|---|
| **安全** | 行追加・削除・並べ替え、新しいユーザー列の追加 | **自動取り込み** |
| **要確認** | 列移動、ヘッダ名変更、対象シート名変更、ヘッダ行移動 | **同期を停止**し、候補提示または再マッピング |
| **破綻** | 必須列消失、ヘッダ候補が複数、対象シート削除、構造を一意に解釈できない | **取り込まず、Excel への書き込みも禁止** |

#### 行追加・削除・並べ替え → 現在行から再構築する

古い DB 行へ差分を適用するのではなく、**Excel の現在行から BOM ビューを再構築**する（§4.5 と同じ考え方）。

```
Excel の現在行
  ↓ supplier・型番・数量・ユーザー列を読む
  ↓ supplier + partNo で DB キャッシュを検索
  ↓ 現在の数量・数量倍率から小計／MOQ 警告を再計算
  ↓ アプリ所有列を合成
BOM ビュー
```

これにより行追加・削除・並べ替え・**同じ型番の複数行**を扱える。行単位の状態を持たない限り**行 ID は不要**。

#### 列追加

次を**すべて満たす**場合のみ、新しい**ユーザー所有列**として自動取り込みする。

- ヘッダが空でない / ヘッダを一意に識別できる / BOM データ領域内の列である / **アプリ所有列の予約名と衝突しない**

ヘッダ重複・予約名衝突・位置を一意に判定できない場合は**自動取り込みせず**、確認・再マッピングへ進む。

#### ヘッダ行の移動 → 自動採用しない

1. 保存済みヘッダ位置と必須列を照合 → 2. 不一致ならシート内から候補を検索 →
3. 候補が一つだけならユーザーへ提示 → 4. 複数またはゼロなら再マッピング →
5. **ユーザーが確定するまで Excel へ書き込まない**

> 例: 「以前のヘッダ行は5行目でしたが、現在は8行目に同じ列構成が見つかりました。新しい位置として採用しますか？」

#### アプリ所有列の移動・削除

- 一意に識別できる移動は**候補として追従可能**
- 削除・名称変更・重複・予約名衝突・**数式入力**があれば**同期停止**し、次を提示する
  - アプリ所有列を再作成 / 現在の列をアプリ所有列として再指定 / EC 項目とのリンクを解除 / BOM リンク全体を解除

## 5. MVP の境界

### 対象

- **`.xlsx` のみ**（`write_grid` は元々 xls/ods への書き出しに非対応なので自然な制約）
- **ローカルファイル**を前提。クラウド同期パスは**検知して警告**（§6.2）
- **単一ユーザー**。同時に触るのは1人という運用前提（§6.0）

### 確定ルール

1. **アプリは読み取り専用**。編集は Excel に集約する（§4.8）
2. **アプリが書くのはアプリ所有列だけ**。ユーザー列は一切書かない（§4.3）
3. **ロックは保持しない**。読みは常時可、書きは Excel が閉じている時のみ（§4.2）
4. **「Excel で編集」ボタンは Excel を起動するだけ**（ロックも受け渡しも無い）
5. **Excel の保存を検知して自動再読込**する（安全判定が「安全」の時のみ自動適用）。
   手動の「更新」ボタンも併置する（§4.2.3）
6. Excel での**行追加・削除・並べ替えは安全判定後に自動取り込み**（§4.9）
7. **新規列は安全判定後にユーザー所有列として取り込み**
8. **列移動・名称変更は一意に判定できても自動確定せず候補提示**
9. **ヘッダ行移動は確認必須**
10. **必須列消失・候補重複・構造不明時は同期停止**
11. **構造確認完了まで Excel へ絶対に書き込まない**
12. **アプリ所有列の Excel 値は DB へ取り込まず、EC 取得結果から再生成**（§4.3）
13. **アプリが1セルでも書いたら全数式セルを `stale`**。`stale`/`missing` は業務利用しない（§4.4.1）
14. **初回読込値は `unverified`**（業務利用可・未検証を明示）。`trusted` は「再計算後に保存されたファイルを
    再読込して確認できた」場合のみ（§4.4）
15. **計算状態は DB に永続化**し、再起動しても `stale` を維持する（§4.4.2）
16. **配列・スピル範囲と書き込み対象が交差したら書かない**。範囲を識別できない場合も書かない（§4.4.2）
17. **置換直前に再度指紋照合**し、競合を検出したら競合コピーへ退避して同期停止（**自動復元しない**）（§4.2.2）
18. **反映待ちは latest-wins**。EC 取得世代を保持し、再試行時に再読込して再生成する（§4.2.1）
19. **`truncated`（5,000 行超）なファイルには書かない**（§3.2）
20. 元ファイル直接更新の前に**バックアップまたは一時ファイル検証**（§4.2.2）
21. リンク BOM と従来 BOM を**共存**させる（既存の取込／書き出しは残す）

### MVP 境界は PoC の測定結果で決める（未決）

「アプリが書き込んだら全数式セルが `stale`」は**安全だが、運用が重くなる可能性**がある
（EC 取得のたびに数式列が業務利用不可になる）。**実 BOM でどの程度 `stale` が発生するかを PoC で測り**、
重すぎる場合は次のいずれかを**製品判断**する。

| 選択肢 | 内容 | 備考 |
|---|---|---|
| **1** | リンク BOM では**型番・数量など業務上重要な列に数式を許可しない**（リンク時に検出して警告／拒否） | 制約は明確。ユーザーの当初の要望「数式セルは空欄扱いでよい」を、**黙って空にせず明示的に拒否する**形で規律化したもの |
| **2** | **COM 等でアプリ保存時に Excel 自身へ再計算・保存させる** | §6.4 と同じ手段。不安定要素が多く、本来スコープ外 |

### スコープ外

- **複数人の同時編集**（§6.0 で合意済み。技術的に保証不可能）
- **アプリからの編集全般**（§4.8。本 MVP の中心的な製品判断）
- **数式の依存関係解析**（変更セルに依存する数式のみを `stale` にする）。§4.4.1 のとおり別規模の課題
- **アプリ内での数式再計算**（計算エンジンの実装）
- **手動上書き列**（`採用単価 ?? EC単価`）。§4.3
- 行単位の状態（提案の採否・コメント）と、それに伴う隠し ID 列
- `.xls` / `.ods` / CSV のリンク（CSV は書式がないので将来容易）

## 6. リスク・未決事項

### 6.0 【決定済み】複数人の同時編集は非対応（PR #19 で合意）

**ファイルロックは同一マシン内でのみ有効で、別マシンの Excel には一切効かない。** 2人が別マシンで開けば
Drive / OneDrive は**競合コピー**（`... (1).xlsx`）を静かに生成する。

**合意した前提**:

- 複数人の同時編集は本設計では**防げない**。**スコープ外**とする
- 指紋比較による**検知と警告**（防止ではない）が限界
- 同時に触るのは1人、という**運用前提**の上に成り立つ機能である

**設計上の帰結**: 書き込み直前に**必ず指紋を照合**し（§4.6）、変化していれば**書き込まず**再読込を促す。
**自動マージは行わない**。UI 上でも「同時編集は非対応」であることを明示する。

**将来の緩和策（スコープ外・任意）**: Excel の `~$` オーナーファイルと同様の**協調的なマーカーファイル**を
Drive 上に置けば「他の人が編集中」を高い確率で検知できる。ただし**アドバイザリ**であり、
Drive の同期遅延（秒オーダー）による競合は残るため**保証にはならない**。

### 6.1 【最大】read-modify-write ライブラリが成立するか

`rust_xlsxwriter` は新規作成専用のため使えない。`umya-spreadsheet` 等が候補だが、
**セルを部分更新できても未対応の Excel 要素を保存時に落とす可能性がある**。

ここが成立しなければ**設計ごと見直し**になるため、他に手を付ける前に潰す（§7 ステップ1）。

### 6.2 【中】クラウド同期環境での書き込み

§2 の決定により**ロックを保持しなくなった**ため、当初の懸念（Drive 上で deny-write ロックが効くか）は
**論点から外れた**。残るのは書き込み時の相互作用。

- 同期クライアントがリモートの変更を適用するためにファイルを書くタイミングと、こちらの原子的置換が競合しうる
- Drive のストリーミングドライブ（G:/H:）上で**原子的置換が機能するか**が未検証
- 同期による競合コピーの発生

**成立しなかった場合の退避**: リンクモードの対象を**ローカルディスクのファイルに限定**し、
クラウド同期パスは検知して警告する。

### 6.2.1 【未決】EC 取得失敗時にアプリ所有列の既存値をどうするか

アプリ所有列は「毎回まるごと上書き」（§4.3）だが、**取得に失敗した行**で既存値を空欄にして消すか、
残すかは**未決**。

現時点の暫定方針は「**既存値を残し、『前回値・手動値の可能性あり』と警告する**」（消すより安全）。
ただし古い価格が残り続けるリスクがあるため、**PoC 後に決定**する。

### 6.3 【低】Excel を開いたままの反映

COM 自動化で起動中の Excel インスタンスに直接書けば実現できるが、セル編集中は COM 呼び出しが弾かれるなど
不安定要素が多い。**最初から入れると失敗モードが多すぎて本体の設計検証ができない**ため、
「反映待ち」（§4.2.1）で運用し、必要性が高まってから別途検討する（§5 の製品判断2とも共通）。

### 6.4 期待値の表現

**「常に Excel が最新」ではない。** 正確には「**Excel が書き込み可能になり次第、最新へ同期**」。
ロック・クラッシュ・権限エラーがある以上、完全な即時同期は保証できない。UI 文言もこれに合わせる。

### 7.1 数式 PoC のマトリクス

自動テスト用ワークブックと**実 BOM ファイル**の双方で確認する。

**数式の種類**: 数値式 `=A1*2` ／ 文字列式 `="CBT3-"&A1` ／ 別シート参照 ／ 名前付き範囲 ／
テーブルの構造化参照 ／ `IF`・`SUM`・`XLOOKUP` ／ 日付・真偽値・エラー値 ／ 共有数式・配列数式・
動的配列（スピル）／ 外部ブック参照 ／ **型番列・数量列・注文番号列が数式のケース**

**計算状態**: 自動計算 ／ 手動計算 ／ `<v>` あり ／ `<v>` が空 ／ キャッシュ値が意図的に古い ／
`calcChain.xml` あり・なし

**操作シナリオ**:

1. 無関係なセルだけ更新しても、数式・キャッシュ・書式が消えない
2. **アプリ所有の EC 列を更新した場合も、その列を参照する数式を `stale` と扱う**
3. 再計算フラグを付けたファイルを Excel で開くと全再計算される
4. Excel で保存・終了後、`calamine` で新しい値が読める
5. **Excel を保存せず終了した場合は `stale` のまま残る**
6. **アプリを再起動しても `stale` が維持される**（指紋ベースの復元規則・§4.4.2）
7. read-modify-write 後も**式文字列とセル型が完全に保持される**

**配列数式・動的配列（§4.4.2）**:

8. **配列数式・動的配列の対象範囲を識別できる**（`ref` 等から）
9. **書き込み対象セルと配列／スピル範囲の交差を検出できる**
10. **交差した場合に Excel への書き込みを禁止する**
11. **範囲を安全に識別できない場合も書き込みを禁止する**

### 7.1.1 恒久的に残す回帰テスト

PoC の一時確認で終わらせず、以下は**単体テストとして残す**。特に座標オフセットの誤りは
**例外にならず「誤ったデータ」として通る**（§3.4.1）ため、テストで固定しないと再発を検知できない。

- **値範囲と数式範囲の開始行・開始列が異なる**（§3.4.1 の罠そのもの）
- **疎な数式配置**（飛び飛びに数式がある）
- **複数シート**
- **共有数式・配列数式・動的配列**

### 7.2 構造変更 PoC のマトリクス

§4.9 の判定を実ファイルで検証する。

**安全（自動取り込みできること）**: 行追加 ／ 行削除 ／ 並べ替え ／ 同じ型番が複数行 ／ 新しいユーザー列の追加

**要確認（自動確定せず候補提示になること）**: 列移動 ／ ヘッダ名変更 ／ シート名変更 ／ ヘッダ行移動
／ アプリ所有列の移動

**破綻（取り込まず・書き込み禁止になること）**: 必須列消失 ／ ヘッダ候補が複数 ／ 対象シート削除 ／
アプリ所有列の削除・名称変更・重複 ／ **アプリ所有列に数式が入力された**

**識別・追跡手段**: 定義名（Defined Names）／ Excel テーブルを追跡に使えるか（**既存 BOM を自動テーブル化しない**）
／ `xr:revisionPtr documentId` が移動・改名の検出ヒントとして使えるか（§3.7。**権威にはしない**）

**ファイル監視（§4.2.3）**: Excel の保存で**イベントが何回発火するか**（デバウンス幅の決定）／
原子的置換後も**監視が外れないか**（親ディレクトリ監視の要否）／保存中の読み取り失敗と**リトライ**／
`~$` オーナーファイルのイベントを**除外**できるか／Drive（G:/H:）上で監視イベントが届くか

## 9. 受け入れ条件

1. リンク BOM を開くと Excel から現在の内容が読み込まれ、EC 値は DB から合成して表示される
2. **Excel でファイルを開いたままでも、アプリは読み込みできる** — §3.5
3. **リンク BOM ではセル編集・行追加・複製・行削除・列追加/削除がすべて無効化されている**
   （従来 BOM では従来どおり動作する） — §4.8
4. EC 取得後に「Excel へ反映」すると、**アプリ所有列だけ**が更新され、**他シート・数式・書式・図形が保持される**
5. **Excel が開いている状態で「Excel へ反映」すると「反映待ち」になり、Excel を閉じた後に反映される** — §4.2.1
6. **「Excel で編集」ボタンで Excel が起動し、その間もアプリは閲覧できる**（ロックしない） — §4.2
7. **Excel で編集して保存すると、アプリが自動で再読込して反映する**（「更新」ボタンでも同じ結果）。
   構造が「要確認」「破綻」の場合は**自動適用せず**、UI に提示する — §4.2.3 / §4.9
8. 数式セルは値として `fx` 付きで表示される
9. **アプリが1セルでも書き込んだ時点で、全数式セルが `stale` になる**。`stale` / `missing` の値は
   EC 取得の型番・数量・小計・MOQ 判定・カート投入数量・注文番号・合計に**使われない**（表示のみ・警告付き）— §4.4.1
10. **9 のファイルを Excel で開くと全再計算され、保存 → アプリが再読込した時点で `trusted` に戻る**
    （**Excel を閉じたことではなく、再読込が契機**）。**Excel を保存せず終了した場合は `stale` のまま**残る — §4.4.1
11. **初回読込の数式値は `unverified` として表示され**、「Excel が保存した時点の計算結果」である旨が UI に示される
    （業務利用は可能。残余リスクを明示する） — §4.4
12. **アプリを終了・再起動しても `stale` が維持される**（単純な初回読込で `unverified` に戻らない） — §4.4.2
13. **ユーザーの動的配列がアプリ所有列へスピルしている場合、Excel への書き込みが禁止される**。
    スピル範囲を安全に識別できない場合も書き込まない — §4.4.2
14. **置換直前の指紋照合で外部の変更を検出した場合、書き込まず、一時ファイルを競合コピーとして退避して
    同期を停止する**（自動復元による再上書きをしない） — §4.2.2
15. **Excel を開いたまま EC 取得を複数回行っても、反映は最新状態のみ**（latest-wins）。
    再試行時に Excel を再読込して現在行から再生成する — §4.2.1
16. **同じ型番が複数行あり数量が異なる場合、小計・MOQ 警告が行ごとに正しい値で書かれる** — §4.5
17. **Excel で行を追加・削除・並べ替えて保存すると、アプリが現在行から再構築して正しく表示する** — §4.9
18. **Excel でヘッダ行を移動すると、自動採用されず候補提示になり、確定するまで Excel へ書き込まれない** — §4.9
19. **必須列を消すと同期が停止し、Excel への書き込みが禁止される** — §4.9
20. **アプリ所有列を Excel で手修正しても DB に取り込まれず、次回 EC 取得で再生成される** — §4.3
21. 5,000 行を超えるファイルには書き込まず、明示的に警告する — §3.2
22. 外部で変更されたファイルには、再読込せずに書き込まない — §4.6
23. 外部で変更されていた場合、**自動マージせず**にユーザーへ警告し、再読込を促す — §6.0
24. 既存の従来 BOM（取込／書き出し）の動作に回帰がない
