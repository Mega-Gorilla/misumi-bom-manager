# Excel リンクモード 詳細計画

Excel を BOM の正本として扱い、アプリと Excel の間で**排他的な編集権を受け渡す**ことで、
インポート／エクスポートの手動往復をなくす機能の詳細計画。

- 関連 Issue: [#18](https://github.com/Mega-Gorilla/misumi-bom-manager/issues/18)
- ステータス: **計画中・未着手**（本ドキュメントの合意 → 技術検証 → 実装）

---

## 1. 目的

現状は Excel の**インポート／エクスポート**方式で、DB が正本（system-of-record）。BOM を更新するたびに
手動の取込・書き出しが必要で、Excel とアプリの内容が容易に乖離する。

**Excel を実質的な BOM マスターとして使い、常に最新に保つ**のが目的。

## 2. 結論：作るべきは「同期」ではなく「編集権の受け渡し」

「DB を正本に保ったまま保存時に元 Excel へ書き戻す」＝**双方向同期**は、2つの正本を常に一致させ続ける
という最も難しい問題を引き受けることになる。ユーザーが Excel を編集する前提なら、**Excel を正本と認めた上で
DB を従属させる**のが正しい。

さらに調査の結果、**OS のファイルロックで「同時に2人が書く状態」を物理的に発生させないことが可能**と判明した
（§3.5）。これにより双方向マージ・競合解決・行 ID がすべて不要になる。

アプリは **`.xlsx` を文書として開くエディタ**になる。Excel 自身と同じモデル。

| 状態 | 書き手 | アプリのグリッド | Excel |
|---|---|---|---|
| アプリが編集権を保持 | アプリのみ | 編集可 | 読み取り専用でしか開けない |
| Excel が編集権を保持 | Excel のみ | 読み取り専用ビュー | 通常編集 |

## 3. 調査結果（すべて実測・本計画の根拠）

### 3.1 現行の書き出しは同期に使えない

`src-tauri/src/spreadsheet.rs:161` の `write_xlsx` は既存ブックを開かず `XlsxWorkbook::new()` で
**新規作成**する。元ファイルへ保存すると次が失われる。

- 他シート（`add_worksheet()` を1回しか呼ばない）
- 数式
- 書式・列幅・結合セル・条件付き書式・図形・グラフ
- セル型（全データが `write_string` で**文字列**として書かれる → 数量が文字列になり `SUM` が壊れる）

→ **既存ファイルの一部セルのみを更新する read-modify-write 方式への置換が前提条件**（§7 の技術検証）。

### 3.2 読み込みに 5,000 行の上限がある

`src-tauri/src/spreadsheet.rs:13` の `MAX_ROWS = 5000`。切り捨てられた読み込み結果を元に元ファイルを
書き換えると、**5,000 行目以降を消す**。

→ **`truncated` なファイルには絶対に書かない**ガードが必須。検知には既存の `SheetGrid.truncated` を使う。

### 3.3 列の所有権の混在が実在する

「supplier 列以外は編集可能」（`src/lib/columns.ts`）であり、`ColumnLink.write` により
**取得した EC 値を編集可能なユーザー列へ書き込む**ことができる。

実 DB を調査した結果、これは仮説ではなく**実在**した。

```
bom_id=4388601c…  key=partsName  kind=core  editable=1
  link_field=product.name   link_write=overwrite
```

（BOM 2件中1件。`link_write` を持つ列は全 16 列中この 1 列のみ）

### 3.4 数式セルは Excel が最後に保存したキャッシュ値として読めている

Excel は数式セルに**数式 `<f>` とキャッシュ値 `<v>` の両方**を保存する。実 Excel（COM）で生成した
ファイルの `xl/worksheets/sheet1.xml` を直接確認した結果:

```xml
<c r="A1"><v>4</v></c>
<c r="B1"><f>A1*2</f><v>8</v></c>
<c r="C1" t="str"><f>CONCATENATE("CBT3-",A1)</f><v>CBT3-4</v></c>
```

`calamine` はこの `<v>` を読むため、現行の `read_workbook` は既に値を返している（実測）:

```
ROW0 = ["4", "8", "CBT3-4"]
```

**正確な表現**（初版の「数式セルは『値』として**正しく**読めている」は過剰主張だったため訂正）:

> 数式セルについて、**Excel が最後に保存したキャッシュ値**を読み取れている。ただし、その値が
> **現在の入力セルに対して再計算済みかは、ファイルだけからは保証できない**。

Excel が**手動計算モード**だった場合や、外部ツールが依存セルだけを書き換えた場合、Excel 由来の
ファイルであってもキャッシュが古い可能性がある。→ 計算状態のモデル化が必要（§4.4）。

→ それでも **数式セルを「空欄として取得」する案は回帰**である。数量が `=A1*2` なら数量が空になり
小計・カート投入数量が壊れ、型番が数式なら行が EC 取得の対象外に落ちる。正しい扱いは
**「値として読む・アプリ上で編集不可にする・書き込まない・計算状態を持つ」**（§4.4）。

#### 3.4.1 `calamine` は数式の有無を取得できる（ただし座標系に罠がある）

`calamine 0.26` は `worksheet_range`（値）に加えて **`worksheet_formula`（`<f>` の数式文字列）**を持つ。
現行の `spreadsheet.rs` は `worksheet_range` しか呼んでいないため、**値は読めるがそのセルが数式かどうかを
アプリへ渡していない**。既存 API で拡張可能（実測）:

```
VALUES   = [Float(4.0), Float(8.0), String("CBT3-4")]
FORMULAS = ["A1*2", "CONCATENATE(\"CBT3-\",A1)"]
```

**【実装上の罠・要注意】** 2つの Range は**原点が異なり**、`used_cells()` は**範囲相対座標**を返す。
そのまま添字で対応づけると**静かに1列ずれる**（実測）:

```
VALUES   start=Some((0, 0)) size=(1, 3)   ← A1:C1
FORMULAS start=Some((0, 1)) size=(1, 2)   ← B1:C1（数式のある最初のセルが原点）

-- NAIVE（範囲相対のまま。誤り）--
   f="A1*2"                    paired value=Some(Float(4.0))     ← B1 の式に A1 の値が付く
   f="CONCATENATE(\"CBT3-\",A1)" paired value=Some(Float(8.0))   ← C1 の式に B1 の値が付く

-- start() でオフセット（正しい）--
   f="A1*2"                    abs=(0, 1) paired value=Some(Float(8.0))
   f="CONCATENATE(\"CBT3-\",A1)" abs=(0, 2) paired value=Some(String("CBT3-4"))
```

**必ず `formula_range.start()` を加算して絶対座標に変換してから値と対応づけること。**
これは誤りが例外にならず**誤ったデータとして通る**ため、単体テストで固定する（§7）。

### 3.5 OS レベルの排他は機能する

アプリが `access=ReadWrite, share=Read`（deny-write）でハンドルを保持した状態での実測:

| 他プロセスの操作 | 結果 |
|---|---|
| writer (`access=ReadWrite`) | **BLOCKED** |
| reader (`access=Read, share=ReadWrite`) | **ALLOWED** |
| reader (`access=Read, share=Read`) | BLOCKED |

ハンドル解放後は書き込み可能に戻る。つまり**アプリが掴んでいる間、Excel は読み取り専用でしか開けず保存できない**。
これは運用上の約束ではなく **OS による強制**。

> **未検証**: 実 Excel が「ファイルは使用中です → 読み取り専用で開きますか？」にフォールバックすること自体は
> 目視確認が必要（OS レベルの排他のみ実証済み）。

### 3.6 Google Drive がストリーミングマウントされている

`GoogleDriveFS` 稼働中、**G: / H: がマウント**（OneDrive も稼働）。BOM リストという性質上、
共有ドライブ運用の可能性が高い。

**ロックは同一マシン内でのみ有効**で、別マシンの Excel には一切効かない。
→ これを受け、**複数人の同時編集は非対応**と決定した（§6.0）。

なお §3.5 の排他の実測は**ローカルディスクでの結果**であり、Drive 上でのロック挙動は**未検証**（§6.2）。

### 3.7 信頼できるワークブック識別子は存在しない（実測）

実 Excel が生成した `xl/workbook.xml` を確認した結果:

```xml
<workbook mc:Ignorable="x15 xr xr6 xr10 xr2" …>
  <xr:revisionPtr revIDLastSave="0"
      documentId="8_{EB6920E8-C1D4-4BB6-B81C-C624C468635D}"
      xr6:coauthVersionLast="47" xr10:uidLastSave="{00000000-0000-0000-0000-000000000000}"/>
  <calcPr calcId="191029"/>
</workbook>
```

`documentId` は存在するが、**識別子として信頼できない**。

- `xr`（2014 revision）名前空間は **`mc:Ignorable` に列挙されている**＝任意の拡張。Excel 以外の生成物には無い
- 共同編集のリビジョン用であり、**安定性が保証されない**
- **ファイルをコピーすると複製される**ため、原本とコピーを区別できない

`docProps/custom.xml` は**存在しなかった**（独自プロパティを我々が注入することは可能だが、それは
**ファイルへの書き込み**であり、§5 の「構造確認完了まで Excel へ絶対に書き込まない」およびリンク時の
読み取り専用性と衝突する）。

| 候補 | 評価 |
|---|---|
| ファイルパス | 移動・改名で破綻。**MVP はこれを同一性の根拠とする**（破綻時は再リンクを促す） |
| `xr:revisionPtr documentId` | 上記の理由で**権威にしない**。「移動・改名の検出ヒント」までなら使える可能性（PoC） |
| `docProps/custom.xml` へ独自 GUID を注入 | **書き込みが必要**。リンク時の読み取り専用性と衝突。MVP 外 |
| 内容の指紋 | 保存のたびに変わる。**変更検知には使えるが同一性の根拠にはならない**（§4.7） |

> 副次的な発見: `<x15ac:absPath url="C:\Users\…\Temp\"/>` によりファイルは**元の絶対パスを保持**している。
> 移動検出のヒントになりうるが、Excel 固有・`mc:Ignorable` であり同じ制約を受ける。

**`calcPr` は実在し、`calcMode` 属性は省略されていた**（＝既定の自動計算）。したがって
§4.4.1 の `fullCalcOnLoad` 付与と `calcMode="manual"` 検出は、いずれも**属性レベルで実現可能**
（ライブラリが `calcPr` を保持できるかは §7 の検証対象）。

## 4. 設計

### 4.1 正本の分割（フィールド単位の所有権）

全体で正本を1つに決めるのではなく、**データごとに正本を分ける**。

| データ | 正本 |
|---|---|
| BOM 入力列（型番・数量・品名・注文番号・独自列） | **Excel** |
| EC 取得値・価格履歴・マッピング設定・指紋・同期状態 | **DB** |
| アプリ画面 | Excel と DB を合成したビュー |

DB は BOM 行の正本ではなくなるが、**未保存編集のジャーナル**（autosave 相当）としては保持する（§4.6）。

### 4.2 編集権トークンの受け渡し

「アプリ起動中は Excel 編集禁止」を**運用の約束ではなく OS による強制**として実装する（§3.5）。
アプリを終了せずに Excel で編集したい場合は、**明示的に編集権を渡す**。

1. アプリ起動 → ファイルが未ロックなら **deny-write で掴んで編集権を取得** → グリッド編集可
2. 「**Excel で編集**」ボタン → 保留中の書き込みをフラッシュ → **ロック解放** → Excel を起動
3. アプリは読み取り専用ビューに切り替わり、ロック解放を監視
4. Excel が閉じられたら **再読込 → 編集権を再取得** → グリッドが再び編集可能に

起動時に既に Excel が開いていれば、編集権を取れないので読み取り専用状態で起動して待機する。

**同時編集のみ引き続き禁止**。アプリ起動中の Excel 編集は上記の受け渡しで可能になる。

> **重要**: ロックを保持したままでは**アプリ自身もファイルを保存できない**ことが実測で判明している。
> 保存の方式は §4.9 で扱い、技術検証で決定する。

### 4.3 列は二分する（所有権＝値の作者。`fillEmpty` は同期では成立しない）

**「列の所有権」と「ファイルへの書き込み主体」は別の概念**として定義する。混同すると、実装者が
「ユーザー列を完全 read-only にするのか、グリッドの編集を書き戻すのか」を判断できない。

- **書き込み主体**: 編集権を保持している間、**ファイルへ書くのは常にアプリのみ**（Excel は読み取り専用）
- **列の所有権**: その列の**値を作るのは誰か**

| 分類 | 値の作者 | EC 取得処理 | ユーザーのグリッド編集 | Excel での編集 |
|---|---|---|---|---|
| **アプリ所有列** | EC 取得処理 | **毎回まるごと上書き** | 不可（読み取り専用） | 物理的には可能。ただし**値は取り込まず**、次回取得時に**再生成**される |
| **ユーザー所有列** | ユーザー | **絶対に書かない** | 可。**編集したセルのみ**書く | 編集権を渡せば可 |

アプリ所有列の Excel 上の値は、アプリにとって**再生成可能な派生値**であり、**DB の EC キャッシュ・価格履歴へ
取り込まない**（＝「Excel で編集しない**約束**」ではなく、「編集されても**無視する**」という**強制**）。

- Excel 上の手修正値を MISUMI 取得結果として採用しない
- EC 取得成功時は現在の取得結果で再生成する
- ヘッダ・セル色・コメント等で「**EC 自動更新列／次回取得時に更新**」と明示する

**ユーザーの手動値を業務値として使いたい場合**は、アプリ所有列を直接上書きせず、**別のユーザー所有列**を使う。

| 列 | 所有者 | 用途 |
|---|---|---|
| EC 単価 | アプリ | EC 取得結果 |
| 採用単価／手動単価 | ユーザー | 業務上の上書き値 |
| 小計 | アプリ | `採用単価 ?? EC 単価` から計算 |

> この「上書き列」は**現行アプリに無い新機能**（現状の小計は quote の単価から導出。§4.5）。
> MVP には**含めず**、必要性が出た時点で別途設計する。アプリ所有列内でのセル単位の手動上書きを
> 正式サポートするには、上書き値・出所・日時・解除操作の管理が必要になるため **MVP 外**。

つまり §5 の「ユーザー所有列はユーザーが編集したセルのみ書く」は、**ユーザー自身が作者である値を
アプリが代筆してファイルに書く**という意味であり、**EC 取得処理がユーザー列を書くことは一切ない**。

**`fillEmpty`（空欄補完）は継続同期では成立しない。** 一度アプリがセルを埋めると次回は「空でない」ため
更新対象から外れ、かといって上書きすればユーザーの手入力を消しうる。**「アプリが埋めた値」と
「ユーザーが入力した値」をセル単位で区別できない**以上、値は更新も削除もできず永久に陳腐化する。

`overwrite` / `fillEmpty` / `suggest` は本質的に**インポート時点の一回きりの概念**であり、同期には持ち込めない。

§3.3 で実在が確認された `partsName ← product.name (overwrite)` は、リンクモードでは
**「アプリ所有列として宣言する」か「`suggest` に落とす（アプリ内表示のみ）」の二択**をユーザーに選ばせる。

### 4.4 数式セルの扱い

**次の4つは別々の性質であり、混同してはならない。**

| 性質 | 成立するか |
|---|---|
| 数式を**保持**できる | ○（数式セルに書かなければよい） |
| キャッシュ値を**読める** | ○（`worksheet_range`。§3.4） |
| その値が**現在の正しい計算結果**である | **△ 保証できない**（§3.4・手動計算モード等） |
| アプリが**再計算**できる | **× できない**（OOXML 編集ライブラリに計算エンジンはない） |

したがって、セルごとに**計算状態**を持つ。

| 状態 | 意味 |
|---|---|
| `trusted` | Excel が再計算して保存した値とみなせる。表示・業務利用可 |
| `stale` | アプリが書き込んで以降、再計算されていない。**表示のみ**（業務利用不可） |
| `missing` | `<v>` が無い等で値を取得できない。**業務利用不可** |

**読み取り時の保持項目**（`worksheet_range` と `worksheet_formula` を**同時に**読む。§3.4.1 の座標系の罠に注意）:

- 表示値 / 数式の有無 / 数式文字列 / 計算状態

**アプリ上の扱い**:

- 数式セルには `fx` 表示を付け、**グリッドで編集不可**にする（編集させれば数式が消える）
- **変更されたセルだけを書く**（dirty-cell のみ更新）。触っていない数式セルは無傷のまま残る
- アプリ所有列に数式が入っていた場合は警告する（上書きすると消えるため）
- 初回読込の値は「**Excel が保存した時点の計算結果**」として表示する（絶対的な最新性は保証しない）

#### 4.4.1 数式キャッシュの陳腐化（dirty-cell 更新では解決しない）

`B1 = A1*2` の状態でアプリが **A1 だけ**を書き換えても、OOXML 編集ライブラリは計算エンジンを持たないため
**B1 の `<v>` は古いまま**残る。直後に再読込すると、**数量・小計・カート投入数に古い値を使う**。

これは「数式セルを直接書かない」こととは**別問題**であり、dirty-cell 更新では解決しない。しかも
**アプリ所有列（EC 単価など）を更新するだけでも起きる** — ユーザーが `=EC単価*数量` のような数式を
持っていれば、その `<v>` が陳腐化する。

**アプリが書き込んだ時点で、全数式セルを `stale` とする。**

依存関係グラフを持たないため「変更セルに依存する数式だけ」を正しく特定できない。数式文字列は
`worksheet_formula` で取得できるが、**安全な依存セル解析の自前実装は別規模の課題**であり
（名前付き範囲・構造化参照・`INDIRECT`/`OFFSET` 等で静的解析は破綻する）、MVP では**安全側に倒して
全数式セルを一括で `stale`** にする。

`stale` / `missing` の値は**業務利用しない**:

- EC 取得の型番 / 数量・小計・MOQ 判定 / カート投入数量 / 注文番号 / 合計・集計

表示は可能だが「未再計算」の警告を付ける。

**Excel ファイル側の扱い**:

- 既存の `<f>` を保持し、**数式セルには絶対に書き込まない**
- アプリがセルを書き換えたら、Excel が次回開いた時に再計算する設定を付与する
  （`fullCalcOnLoad`、必要に応じて `forceFullCalc`）
- 計算モード・計算チェーン（`calcChain.xml`）・動的配列・共有数式を RMW ライブラリが保持できるか検証する

**状態遷移**（Excel で再計算しただけではアプリへ結果は戻らないため、
「Excel で再計算 → 保存 → 閉じる → アプリが再読込」までを**一つの遷移**として扱う）:

```
Excel 保存済みキャッシュ
        ↓ アプリが読込
trusted（表示・業務利用可）
        ↓ アプリが Excel へ何か書く
stale（表示のみ。EC 取得・カート投入には使わない）
        ↓ Excel を開いて全再計算 → 保存 → 終了
        ↓ アプリが再読込
trusted
```

Excel を**保存せず**終了した場合は `stale` のまま残る。

**初回リンク時の注意**: Excel が最後に正しく再計算して保存したかを**アプリだけでは証明できない**ため、
UI 上は「**Excel 保存時の計算結果**」と表現する。

> **検討**: `<calcPr calcMode="manual"/>` を検出できればリンク時に警告できる（キャッシュが古い蓋然性が高い）。
> ただしこれは**ヒューリスティックであって証明ではない**（`auto` でも第三者ツールが依存セルを書けば古くなる）。
> PoC で検出可否を確認する。

### 4.5 行 ID は不要（ただし派生列は行単位で計算する）

**訂正**: 初版では「EC 値は**型番の**純粋関数」と書いたが、これは**不正確**だった。実装を確認した結果:

- キャッシュ／履歴のキーは `parts_no` 単独ではなく **`(supplier_code, parts_no)`**（`db.rs` V1）
- キャッシュは **qty 非依存**（代表 qty=1 で取得。`src/api/bom.ts:74-75`）
- `quote.subtotal` は **`unitPrice × Qty × qtyMultiplier`**（`src/lib/columns.ts:159`）
- `messages` の MOQ 警告も**行の Qty に依存**する

既存実装はこれらを保存された値ではなく**行の現在値から都度導出**している
（`src/App.tsx:296-298`: "Subtotal and the MOQ note are derived **LIVE** ... so they stay correct
after the user edits Qty (no stale stamped values)"）。

正しくは、アプリ所有列の値は次の**純粋関数**である。

```
appOwnedValue = f(supplier, partNo, row qty, BOM qtyMultiplier)
```

したがって**書き込み直前に、現在の各行の supplier・型番・数量と BOM の数量倍率から再計算する**
（既存実装の LIVE 導出と同じ方針）。これにより:

- 同じ型番でも**行ごとに異なる値**（小計・MOQ 警告）を正しく書ける
- 依然として**冪等**であり、**行の同一性を必要としない**（行 ID 不要の結論は維持）

**行 ID が必要になるのは行単位の状態を持つ場合**（提案の採否、アプリ独自コメント、型番変更前後の行追跡）。
MVP では持たない。将来必要になれば隠し ID 列またはメタデータシートを検討する。

### 4.6 クラッシュと未保存編集

ロック自体は OS がプロセス終了時に解放するので残らないが、未書き込みの編集は失われる。
そこで **DB を編集ジャーナル（未保存バッファ）として使う**。DB は BOM の正本ではなく autosave 的な役割。

再起動時、ファイルの指紋が**最後に成功したフラッシュ時のものと一致**していればジャーナルを再適用でき、
**異なれば**外部で変更されているので破棄を促す。

### 4.7 書き込み前の指紋照合

**DB と Excel を1つのトランザクションにはできない。** 「DB 保存成功・Excel 更新失敗」は必ず起こり得るため、
**「反映待ち」状態は設計の一部**であって例外処理ではない（ロック制御により発生頻度は激減する）。

書き込み直前に**最終読込時の指紋と現在の指紋を比較**する。変化していれば古い行番号を信用せず、
**再読込 → EC 列を再計算 → 書き込み**。ファイル監視は**通知用**であり、整合性保証には使わない。

### 4.8 同期メタデータ

現在 `importedFrom`（ファイルパス）しか保持していない（`src/bom/ImportWizard.tsx:184`）。

リンク作成・再確認時に、**構造契約**として最低限これらを DB へ保存する（§4.11 の判定に必要）。

- **ワークブック識別子** — ただし §3.7 のとおり信頼できる識別子は存在しない。**MVP はパスを同一性の根拠**とし、
  破綻時（移動・改名）は再リンクを促す
- 対象シート（名前またはシート ID）
- ヘッダ行・データ開始行
- **必須列・任意列**
- Excel 列 ↔ アプリ列キーの対応
- 読み飛ばした列
- 各列の role
- **アプリ所有／ユーザー所有**
- アプリ所有列の位置
- **最後に確認したヘッダ構成**
- **データ範囲**
- **構造フィンガープリント**（§4.11 の変更検知用。内容の指紋（§4.7）とは別物）
- 同期状態とエラー（反映待ちを含む）

> 定義名（Defined Names）や Excel テーブルを追跡手段として使えるかは **PoC 対象**（§7）。
> ただし**既存 BOM を自動的にテーブル化してレイアウトへ影響を与えない**こと。

### 4.9 編集権ロックと保存の両立

**deny-write ハンドルを保持したままでは、アプリ自身もファイルを保存できない。** 実測結果:

| 保持ハンドルの share | 同一プロセスの write-open | 原子的置換（`File.Move` overwrite） | 他プロセスの書き込み |
|---|---|---|---|
| `Read` | BLOCKED | BLOCKED | BLOCKED |
| `Read,Delete` | BLOCKED | **BLOCKED** | BLOCKED |

`share=Read` は**別プロセスだけでなく同一プロセスの再オープンにも適用される**。一般的な
read-modify-write クレートは**パスを再オープンする**ため、**ロックを保持したままでは動作しない**。
`FILE_SHARE_DELETE` を許可しても（.NET `File.Move` で検証した限り）原子的置換は救済されなかった。

> ネイティブ `ReplaceFileW` / `MoveFileEx` は .NET の `File.Move` と挙動が異なる可能性があるため断定はしない。
> §7 の技術検証項目とする。

方式の候補（技術検証で決定する）:

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A: ハンドル渡し** | 保持中のハンドルを `Write + Seek` ストリームとしてライブラリへ渡し **in-place 更新** | ロックを一度も手放さない ＝ **TOCTOU なし** | ライブラリが**ストリーム書き込みに対応**している必要がある。truncate + 全書き直しとなり**原子性がない**（書き込み中のクラッシュでファイル破損）→ **事前バックアップ必須** |
| **B: 一時解放** | 保存時だけロックを解放 → **指紋照合** → 一時ファイルへ書いて**原子的置換** → **再取得** | 原子的置換が使え、**パス指定のライブラリがそのまま使える** | 解放〜再取得の間に **TOCTOU 窓**（他プロセスが掴む／書く可能性） |

**現時点の推奨は B**（原子性を優先。TOCTOU 窓はミリ秒オーダーで、**再取得時の指紋再照合により検知可能**。
検知した場合は書き込みを破棄して再読込を促す）。ただし A が成立すれば TOCTOU を完全に消せるため、
**§7 の技術検証で両案を評価**して決める。

いずれの案でも **§4.7 の指紋照合**と**書き込み前のバックアップ**（§5）は必須。

### 4.10 アプリはセル値の編集のみ（構造操作は Excel 限定）

リンク BOM では、アプリ上で許可するのは**セル値の編集だけ**とする。次の**構造操作は Excel 側に限定**する。

- 行の追加・削除・並べ替え
- 列の追加・削除・移動・名称変更
- **数式の作成・変更**（アプリは既存数式を値として表示するのみ。§4.4）

**既存機能への影響（無視できない）**: 現行アプリは以下を持っており、リンク BOM では**すべて無効化**される。

| 機能 | 場所 |
|---|---|
| 行追加 / 複製 / 行削除 | `src/bom/Toolbar.tsx:196-200`（メニュー）、`:296-299`（コマンドバー） |
| 列の追加・削除 | `src/bom/ColumnManager.tsx:172` ほか |

結果として、リンクモードのアプリに残るのは **EC 価格・納期の取得／履歴閲覧／合計／カート投入／セル値の編集**
となる。従来 BOM ではこれらの機能は従来どおり使える（両モードは共存する。§5）。

> 数量倍率（`meta.qtyMultiplier`）は Excel ではなく **DB 所有のメタ情報**なので、リンクモードでも編集可能。

### 4.11 Excel 側の構造変更判定

Excel 側ではユーザーが行・列・数式を**自由に編集してよい**。ただし**編集権がアプリへ戻った時点で構造を検証**し、
**安全性を確認できるまで Excel へ書き戻さない**。**不明な構造を推測して同期しない**ことが本節の中心。

| 判定 | 変更例 | 動作 |
|---|---|---|
| **安全** | 行追加・削除・並べ替え、新しいユーザー列の追加 | **自動取り込み** |
| **要確認** | 列移動、ヘッダ名変更、対象シート名変更、ヘッダ行移動 | **同期を停止**し、候補提示または再マッピング |
| **破綻** | 必須列消失、ヘッダ候補が複数、対象シート削除、構造を一意に解釈できない | **取り込まず、Excel への書き込みも禁止** |

#### 行追加・削除・並べ替え → 現在行から再構築する

古い DB 行へ差分を適用するのではなく、**Excel の現在行から BOM ビューを再構築**する（§4.5 と同じ考え方）。

```
Excel の現在行
  ↓ supplier・型番・数量・ユーザー列を読む
  ↓ supplier + partNo で DB キャッシュを検索
  ↓ 現在の数量・数量倍率から小計／MOQ 警告を再計算
  ↓ アプリ所有列を合成
BOM ビュー
```

これにより行追加・削除・並べ替え・**同じ型番の複数行**を扱える。行単位の状態を持たない限り**行 ID は不要**。

#### 列追加

次を**すべて満たす**場合のみ、新しい**ユーザー所有列**として自動取り込みする。

- ヘッダが空でない / ヘッダを一意に識別できる / BOM データ領域内の列である / **アプリ所有列の予約名と衝突しない**

ヘッダ重複・予約名衝突・位置を一意に判定できない場合は**自動取り込みせず**、確認・再マッピングへ進む。

#### ヘッダ行の移動 → 自動採用しない

1. 保存済みヘッダ位置と必須列を照合 → 2. 不一致ならシート内から候補を検索 →
3. 候補が一つだけならユーザーへ提示 → 4. 複数またはゼロなら再マッピング →
5. **ユーザーが確定するまで Excel へ書き込まない**

> 例: 「以前のヘッダ行は5行目でしたが、現在は8行目に同じ列構成が見つかりました。新しい位置として採用しますか？」

#### アプリ所有列の移動・削除

- 一意に識別できる移動は**候補として追従可能**
- 削除・名称変更・重複・予約名衝突・**数式入力**があれば**同期停止**し、次を提示する
  - アプリ所有列を再作成 / 現在の列をアプリ所有列として再指定 / EC 項目とのリンクを解除 / BOM リンク全体を解除

## 5. MVP の境界

### 対象

- **`.xlsx` のみ**（`write_grid` は元々 xls/ods への書き出しに非対応なので自然な制約）
- **ローカルファイル**を前提。クラウド同期パスは**検知して警告**
- **単一ユーザー**。同時に触るのは1人という運用前提

### 動作

- リンク BOM と従来 BOM を**共存**させる（既存の取込／書き出しは残す）
- アプリが編集権を保持している間のみグリッド編集可
- アプリ所有列のみ書き戻す。ユーザー所有列は**ユーザーが編集したセルのみ**書く
- 数式セルは値として読み、`fx` 表示・編集不可・書き込まない。**アプリが書き込んだら全数式セルを `stale`**、
  `stale` / `missing` は業務利用しない（§4.4）
- `truncated`（5,000 行超）なファイルには書かない
- 元ファイル直接更新の前に**バックアップまたは一時ファイル検証**

### 確定ルール

1. **アプリ上ではセル値だけ編集可能**（§4.10）
2. **数式・行列構造の変更は Excel のみ**
3. Excel での**行追加・削除・並べ替えは安全判定後に自動取り込み**（§4.11）
4. **新規列は安全判定後にユーザー所有列として取り込み**
5. **列移動・名称変更は一意に判定できても自動確定せず候補提示**
6. **ヘッダ行移動は確認必須**
7. **必須列消失・候補重複・構造不明時は同期停止**
8. **構造確認完了まで Excel へ絶対に書き込まない**
9. **アプリ所有列の Excel 値は DB へ取り込まず、EC 取得結果から再生成**（§4.3）
10. 手動値を業務利用する場合は**別のユーザー所有「上書き列」**を使う（MVP 外・§4.3）

### MVP 境界は PoC の測定結果で決める（未決）

「アプリが書き込んだら全数式セルが `stale`」は**安全だが、運用が重くなる可能性**がある
（EC 取得のたびに数式列が業務利用不可になる）。**実 BOM でどの程度 `stale` が発生するかを PoC で測り**、
重すぎる場合は次のいずれかを**製品判断**する。

| 選択肢 | 内容 | 備考 |
|---|---|---|
| **1** | リンク BOM では**型番・数量など業務上重要な列に数式を許可しない**（リンク時に検出して警告／拒否） | 制約は明確。ユーザーの当初の要望「数式セルは空欄扱いでよい」を、**黙って空にせず明示的に拒否する**形で規律化したもの |
| **2** | **COM 等でアプリ保存時に Excel 自身へ再計算・保存させる** | §6.4 と同じ手段。不安定要素が多く、本来スコープ外 |

### スコープ外

- **複数人の同時編集**（§6.0 で合意済み。技術的に保証不可能）
- **数式の依存関係解析**（変更セルに依存する数式のみを `stale` にする）。§4.4.1 のとおり別規模の課題
- **アプリ内での数式再計算**（計算エンジンの実装）
- Excel を開いたまま反映する COM / Excel アドイン方式（§6.4）
- 行単位の状態（提案の採否・コメント）と、それに伴う隠し ID 列
- `.xls` / `.ods` / CSV のリンク（CSV は書式がないので将来容易）

## 6. リスク・未決事項

### 6.0 【決定済み】複数人の同時編集は非対応（PR #19 で合意）

**OS ロックは同一マシン内でのみ有効で、別マシンの Excel には一切効かない。** 2人が別マシンで開けば
双方が「排他ロック」を取得でき、Drive / OneDrive は**競合コピー**（`... (1).xlsx`）を静かに生成する。

**合意した前提**（PR #19）:

- 複数人の同時編集は本設計では**防げない**。**スコープ外**とする
- 指紋比較による**検知と警告**（防止ではない）が限界。「他者が変更した」ことを事後に知らせるまでが責任範囲
- 同時に触るのは1人、という**運用前提**の上に成り立つ機能である

**設計上の帰結**:

- 編集権の取得時とファイル書き込みの直前に**必ず指紋を照合**する（§4.7）
- 指紋が変化していれば**書き込まず**、再読込を促す。**自動マージは行わない**
- UI 上でも「同時編集は非対応」であることを明示する（§6.5 の期待値表現と一体）

**将来の緩和策（スコープ外・任意）**: Excel の `~$` オーナーファイルと同様の**協調的なマーカーファイル**を
Drive 上に置けば、「他の人が編集中」を高い確率で検知できる。ただしこれは**アドバイザリ**であり、
Drive の同期遅延（秒オーダー）による競合は残るため**保証にはならない**。採用するとしても検知の精度向上が目的。

### 6.1 【最大】read-modify-write ライブラリが成立するか

`rust_xlsxwriter` は新規作成専用のため使えない。`umya-spreadsheet` 等が候補だが、
**セルを部分更新できても未対応の Excel 要素を保存時に落とす可能性がある**。

ここが成立しなければ**設計ごと見直し**になるため、他に手を付ける前に潰す（§7 ステップ 2）。

### 6.2 【高】クラウド同期環境でのロック挙動（未検証）

§6.0 で「複数人の同時編集は非対応」と合意したが、**それとは別に技術的な未検証項目が残る**。
単一ユーザーであっても、ファイルが Drive 上にある限り以下は成立が不明。

- Google Drive の**ストリーミングドライブ（G:/H:）上での deny-write ロックの実挙動**。仮想ファイルシステムの
  ため、ロック意味論が通常のディスクと異なる可能性がある（§3.5 の実測は**ローカルディスクでの結果**）
- 同期クライアントがリモートの変更を適用するためにファイルを書こうとしたとき、こちらが deny-write で
  掴んでいると**同期が失敗・遅延する**可能性がある
- 同期クライアントがファイルを置き換える形で更新した場合、こちらが保持しているハンドルが**無効化される**可能性がある

**成立しなかった場合の退避**: リンクモードの対象を**ローカルディスクのファイルに限定**し、クラウド同期パスは
検知して警告する（リンク自体を拒否するか、ロックなしの読み取り専用リンクに落とす）。

→ §7 ステップ 1 で最初に潰す。

### 6.2.1 【未決】EC 取得失敗時にアプリ所有列の既存値をどうするか

アプリ所有列は「毎回まるごと上書き」（§4.3）だが、**取得に失敗した行**で既存値を空欄にして消すか、
残すかは**未決**。

現時点の暫定方針は「**既存値を残し、『前回値・手動値の可能性あり』と警告する**」（消すより安全）。
ただし古い価格が残り続けるリスクがあるため、**PoC 後に決定**する。

### 6.3 【中】読み取り専用からの「名前を付けて保存」

ユーザーが Excel で読み取り専用のまま編集し、別名保存すればコピーが分岐する。**防げない。**
UI 誘導（アプリの「Excel で編集」を使わせる）と、編集権の再取得時の指紋比較による検知が限界。

### 6.4 【低】Excel を開いたままの反映

COM 自動化で起動中の Excel インスタンスに直接書けば実現できるが、セル編集中は COM 呼び出しが弾かれるなど
不安定要素が多い。**最初から入れると失敗モードが多すぎて本体の設計検証ができない**ため、
編集権の受け渡し（§4.2）で運用し、必要性が高まってから別途検討する。

### 6.5 期待値の表現

**「常に Excel が最新」ではない。** 正確には「**Excel が書き込み可能になり次第、最新へ同期**」。
ロック・クラッシュ・権限エラーがある以上、完全な即時同期は保証できない。UI 文言もこれに合わせる。

### 7.1 数式 PoC のマトリクス（ステップ4）

自動テスト用ワークブックと**実 BOM ファイル**の双方で確認する。

**数式の種類**: 数値式 `=A1*2` ／ 文字列式 `="CBT3-"&A1` ／ 別シート参照 ／ 名前付き範囲 ／
テーブルの構造化参照 ／ `IF`・`SUM`・`XLOOKUP` ／ 日付・真偽値・エラー値 ／ 共有数式・配列数式・
動的配列（スピル）／ 外部ブック参照 ／ **型番列・数量列・注文番号列が数式のケース**

**計算状態**: 自動計算 ／ 手動計算 ／ `<v>` あり ／ `<v>` が空 ／ キャッシュ値が意図的に古い ／
`calcChain.xml` あり・なし

**操作シナリオ**:

1. 無関係なセルだけ更新しても、数式・キャッシュ・書式が消えない
2. 数式の参照元セルを更新すると、アプリは古いキャッシュを**業務利用しない**
3. **アプリ所有の EC 列を更新した場合も、その列を参照する数式を `stale` と扱う**
4. 再計算フラグを付けたファイルを Excel で開くと全再計算される
5. Excel で保存・終了後、`calamine` で新しい値が読める
6. **Excel を保存せず終了した場合は `stale` のまま残る**
7. read-modify-write 後も**式文字列とセル型が完全に保持される**
8. `worksheet_range` と `worksheet_formula` の**座標系オフセット**が正しく扱われている（§3.4.1 の罠）

> 8 は誤りが例外にならず**誤ったデータとして通る**ため、単体テストで固定する。

### 7.2 構造変更 PoC のマトリクス（ステップ4と同時）

§4.11 の判定を実ファイルで検証する。

**安全（自動取り込みできること）**: 行追加 ／ 行削除 ／ 並べ替え ／ 同じ型番が複数行 ／ 新しいユーザー列の追加

**要確認（自動確定せず候補提示になること）**: 列移動 ／ ヘッダ名変更 ／ シート名変更 ／ ヘッダ行移動
／ アプリ所有列の移動

**破綻（取り込まず・書き込み禁止になること）**: 必須列消失 ／ ヘッダ候補が複数 ／ 対象シート削除 ／
アプリ所有列の削除・名称変更・重複 ／ **アプリ所有列に数式が入力された**

**識別・追跡手段**: 定義名（Defined Names）／ Excel テーブルを追跡に使えるか（**既存 BOM を自動テーブル化しない**）
／ `xr:revisionPtr documentId` が移動・改名の検出ヒントとして使えるか（§3.7。**権威にはしない**）

## 9. 受け入れ条件

1. リンク BOM を開くと Excel から現在の内容が読み込まれ、EC 値は DB から合成して表示される
2. アプリが編集権を保持している間、Excel は読み取り専用でしか開けない
3. 「Excel で編集」でロックが解放され、Excel で保存でき、閉じるとアプリが再読込して編集権を取り戻す
4. EC 取得後に「Excel へ反映」すると、**アプリ所有列だけ**が更新され、**他シート・数式・書式・図形が保持される**
5. 数式セルは値として `fx` 付きで表示され、グリッド上で編集できない
6. **アプリが1セルでも書き込んだ時点で、全数式セルが `stale` になる**。`stale` / `missing` の値は
   EC 取得の型番・数量・小計・MOQ 判定・カート投入数量・注文番号・合計に**使われない**（表示のみ・警告付き）— §4.4.1
7. **6 のファイルを Excel で開くと全再計算され、保存・終了 → アプリが再読込した時点で `trusted` に戻る**。
   **Excel を保存せず終了した場合は `stale` のまま**残る — §4.4.1
8. **同じ型番が複数行あり数量が異なる場合、小計・MOQ 警告が行ごとに正しい値で書かれる** — §4.5
9. **Excel で行を追加・削除・並べ替えて閉じると、アプリが現在行から再構築して正しく表示する** — §4.11
10. **Excel でヘッダ行を移動すると、自動採用されず候補提示になり、確定するまで Excel へ書き込まれない** — §4.11
11. **必須列を消すと同期が停止し、Excel への書き込みが禁止される** — §4.11
12. **アプリ所有列を Excel で手修正しても DB に取り込まれず、次回 EC 取得で再生成される** — §4.3
13. **リンク BOM では行追加・複製・行削除・列追加/削除が無効化されている**（従来 BOM では従来どおり動作する） — §4.10
14. 5,000 行を超えるファイルには書き込まず、明示的に警告する
15. 外部で変更されたファイルには、再読込せずに書き込まない
16. 外部で変更されていた場合、**自動マージせず**にユーザーへ警告し、再読込を促す（§6.0）
17. 既存の従来 BOM（取込／書き出し）の動作に回帰がない
